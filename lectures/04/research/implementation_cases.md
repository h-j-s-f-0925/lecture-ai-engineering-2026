# 第4回 実装宿題：作問メモ

このメモで既存の評価セットと採点結果を確認しながら、自分の評価セット10件を設計・確認する。候補をそのまま採用するのではなく、自分のエージェントが実際に参照できるデータと、採点時に人・LLMが確認できる根拠を確かめる。確定した質問・期待値を `annotate.py` に入力し、実際の評価データは `data/eval/my_cases.jsonl` に作る。

## 作問するときに決める項目

`annotate.py` の「作問（宿題・実装）」フォームに合わせ、1件ごとに次の順で入力する。

1. **質問**：自分のエージェントに実際に尋ねる文
2. **種類**：正常系、表記ゆれ、用語集にない語、宿題の答え、講座外、誤入力など
3. **期待するふるまい**：回答で確認したい事実・条件を、採点時に判定できる形で1〜2文で書く
4. **参照する用語集のエントリ**：関係する項目があれば選ぶ。なければ空欄

回答の根拠となる講義要点などはフォームの入力欄ではないため、作問時の確認メモとして別に記録する。講義資料を根拠にする場合は、資料で確認した具体的な事実を「期待するふるまい」にも含める。

正常系だけでなく、情報が足りない質問や誤った前提を含む質問も入れる。既存の質問をそのまま再利用せず、同じ種類を扱う場合も質問の内容を変える。質問を作る前に、下の「候補を採用する前に確認すること」を必ず確認する。

## 候補を採用する前に確認すること

このリポジトリには、エージェントが回答に使うデータと、評価時に採点者へ見せる参照データがある。**データがリポジトリに存在するだけでは、採点者がその内容を見て正誤を判定できるとは限らない。**

| データ | エージェントが使う方法 | 作問・ラベル付け・LLM採点で見えるか |
|---|---|---|
| 用語集 [`data/glossary.json`](../../../data/glossary.json) | `search_glossary` が検索する | ケースの「参照する用語集」でIDを選ぶと、人のラベル画面とLLM採点の参照に定義が表示される |
| 講義要点 [`data/lectures/`](../../../data/lectures/) | `get_lecture_summary` が対応するMarkdownを読む | 現在のケース形式には講義要点を選ぶ欄がなく、ラベル画面とLLM採点にも本文は自動表示されない |
| ケースの「期待するふるまい」 | エージェントに渡すデータではない | ラベル画面とLLM採点の両方に表示・入力される。講義資料を根拠にする場合は、資料で確認した合格条件をここに具体的に書く |

現在の `app/agent.py` は用語集検索と講義要点取得の両方をツールとして登録しており、[`data/lectures/`](../../../data/lectures/)には第1・2・3・4・6回の要点があります。ただし、[`app/judge.py`](../../../app/judge.py) の採点参照は用語集の登録項目と「期待するふるまい」です。講義要点のファイルを採点者に渡す実装ではありません。また、現在の「根拠」基準は用語集を中心に書かれています。

そのため、宿題では次の順で選びます。

1. **自分のエージェントが使えるデータか確認する。** 質問に必要な用語・回の資料が実際にあるか、または正しく「ない」と答える想定かを確かめる。
2. **採点者が判定できる根拠か確認する。** 用語集の項目なら参照IDを選ぶ。講義要点を使う質問なら、該当する要点を読んだうえで、期待欄に資料名と回答に必要な具体的事実を書く。
3. **期待欄だけでは判定しにくいケースは選ばない。** 「資料に基づいて答える」のような抽象的な期待だけでは、採点者は資料との一致を確認できない。特に講義内容の細かな正確さを測りたい場合、現行の採点画面・ルーブリックでは不十分になりうる。今回の宿題では、参照が明確な用語集中心のケースを優先する。
4. **実装していない機能や、実データのない内容を評価しない。** クイズ・保存・複数ターンなどは、自分のエージェントにその機能があるか、今の評価手順で成否を観察できるかを確認する。観察できない機能は、回答評価10件ではなく別のテストに分ける。

例：第3回の要点を尋ねるケースは、エージェントが `data/lectures/03.md` を読めるため回答は生成できます。しかし評価時に同ファイルは自動表示されません。使う場合は、実際に同ファイルを確認して、期待欄に「ツール呼び出しをしたこと」ではなく、回答に必要な要点を具体的に記します。ツール呼び出し自体を確かめたい場合は `--trace` など別の手段を使います。

作問の参考になる不一致：

## 既存10件にないケース候補

既存セットは用語の説明・比較や、表記ゆれ、用語集外、宿題、講座外、指示無視、誤入力、存在しない回を扱っている。次の候補は同じ質問の言い換えではなく、エージェントの別機能や境界を確かめるためのもの。10件すべてを埋める必要はなく、自分のエージェントに関係するものを選ぶ。

ここでいう**正常系**は、講座資料に情報があり、通常の使い方で回答できる質問。**異常系・境界系**は、質問の曖昧さ、前提の誤り、資料の欠落、制約の衝突など、通常どおりには答えにくい質問を指す。単に「拒否できるか」だけでなく、不確かな部分を示しつつ答えられる部分は答えるケースも含める。

### この評価セットで測れる範囲

- [judge.py](../../../app/judge.py) は、各ケースの質問を独立してエージェントに渡し、生成回答を保存する。会話履歴を使う複数ターンの「続きの質問」は、この形式のままでは正しく評価できない。試すなら一つの質問だけで内容が分かる形にするか、対話履歴を扱う別のテストに分ける。
- この評価セットで主に比べるのは回答文であり、内部のツール呼び出しや引数までは採点しない。適切なツールを選んだか調べたい場合は、`app.agent --trace` や既存のツール単体テストも使う。
- 学習ログ保存はファイルを書き込む副作用があり、承認が必要。[judge.py](../../../app/judge.py) の自動生成処理は承認のやりとりを完了する用途ではないため、保存の承認・拒否は [test_agent.py](../../../tests/test_agent.py) のような隔離したテスト、または対話実行で別に確かめる。
- APIキー不足、レート制限、通信失敗などは質問の種類ではなく実行環境の障害なので、評価セットの10件ではなく別の動作確認で扱う。

これらの分類は、評価データを実際の利用に近づける考え方（[OpenAIの評価ガイド](https://developers.openai.com/api/docs/guides/evals)）、ツール呼び出しや会話状態も含めたエージェント評価（[Google Cloudのエージェント評価](https://docs.cloud.google.com/gemini-enterprise-agent-platform/optimize/evaluation/agent-evaluation)）、指示の埋め込みや過剰な権限に関するリスク（[OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)、[LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)）を参考に、この講座のエージェント向けに整理した候補。

## 入力・評価の手順

1. 上の10件を読み、根拠・質問・期待値が自分の意図に合うか最終確認する。各質問について、エージェントが使うデータ・機能があることと、期待値で回答の正誤を判定できることを確かめる。1件につき主に試すふるまいを1つ決め、独立した要件を詰め込みすぎない。根拠を特定できないケースは、質問を直すか別の候補に置き換える。
2. `uv run --with streamlit==1.66.1 streamlit run tools/annotate.py` を起動し、「作問（宿題・実装）」の保存先を `data/eval/my_cases.jsonl` にして入力する。関係する用語集IDは選択する。講義要点など専用欄のない資料は、内容を確認して具体的な合格条件を「期待するふるまい」に書く。資料名だけでは採点根拠にならない。
3. 10件を入力したら、JSONLを回答生成前に別名でコピーしておく。`--generate` はケースファイル内の回答欄を自分のエージェントで上書きする。
4. `uv run python -m app.judge --generate --cases data/eval/my_cases.jsonl` で回答を生成する。このコマンドが使うのは `app/agent.py` のエージェントである。自分のエージェントの変更がこのファイルに反映されていることを確認する。
5. 「ラベル付け」で評価セットを `data/eval/my_cases.jsonl`、ラベルの保存先を `lectures/04/my_labels.jsonl` にして、人のラベルを付ける。採点画面に表示される参照と期待値を使い、判断できないときは「迷った」にチェックする。
6. `uv run python -m app.judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --out lectures/04/my_judge_result.json` で採点する。講義資料の事実を含むケースは、期待欄に書いた条件を採点者が根拠として使える具体性か、不一致例を見て確認する。
7. 一致率・coverage・要確認・不一致を確認する。10件では1件の差が10ポイントになるため、率だけで結論を出さず、具体例と併記する。
8. 結果と「コードで判定する基準／LLMに任せる基準」の使い分け、参照データ上の制約を [answer.md](../answer.md) の宿題欄にまとめる。回答生成に使ったモデルと採点モデルは別々に記録する。ツール呼び出しやファイル状態を確認していない場合、それらまで評価したとは書かない。

## 調査から取り入れられる追加の工夫

以下は宿題の必須要件を増やすものではなく、作問と結果の信頼性を上げるために選べる工夫である。GPQA・HLEの問題レビュー、SWE-benchの実行可能性確認、τ²-benchの状態検証を、この小規模な宿題に合わせて取り入れる（詳しくは[調査レポート](./20261113_2234_eval-set-benchmark-lessons.md)）。

### 回答を生成する前に10件をレビューする

自分で各ケースを一度読み、次を確認する。可能なら数件だけでも他の人にも読んでもらう。

- **根拠がある**：質問に必要な情報がエージェントのデータにあるか、または「情報がない」と判定するケースか明確。
- **質問が明確**：質問の対象・条件が特定でき、意図しない複数の解釈がない。
- **期待値で判定できる**：合格に必要な内容と、避けるべき誤りが具体的。回答例の一字一句ではなく、意味上の条件を書く。
- **失敗の原因を追える**：まずは1件で主に1つのふるまいを試す。複合依頼は、個別の要件を試した後に追加する。
- **採点方法が合っている**：文字数・項目数など決定的な条件はコード、意味の妥当性はLLMと人、ツール実行・ファイル状態・複数ターンは別の統合／対話テストにする。

質問の作成と期待値の確定を回答生成より先に行う。生成回答を見てから期待値を合わせると、その回答を正当化する基準になりやすい。これは作問とレビューを分けるベンチマークの考え方を宿題向けに縮小したもの。

### 必要な場合だけ回答の揺れを確認する

LLMの回答は実行ごとに変わる場合がある。再現性や揺れを調べたいケースだけ、回答生成を複数回行って結果を比較する。`--generate` は同じケースファイルを上書きするため、各回の前にコピーを残し、モデル名と実行回を対応づける。複数回の結果をまとめる場合は、成功回数と試行回数を両方記録する。API呼び出しが増えるので、10件すべてに繰り返す必要はない。

10件では1件の差が10ポイントになる。結果は選んだケース上の診断として報告し、他の質問や利用場面全体に一般化しない。同じ10件とルーブリックを何度も調整した場合は、そのケースに合わせ込みが起きうることも記す。
