# 第4回宿題の評価セット作成に活かせるベンチマーク設計の調査

- 調査日：2026年11月13日（JST）
- 対象：正常系30件・異常系30件の作問候補、実装宿題の評価手順、添付画像にある4ベンチマーク
- 目的：候補を10件に絞るときの分類軸、質問・期待値の作り方、採点方法を整理する

## 結論

4つのベンチマークは、同じ形式の「質問集」ではない。GPQAとHumanity’s Last Exam（HLE）は答えを確認できる知識問題、SWE-bench Verifiedは実際のコード修正とテスト、τ²-bench（タウ・スクエアド・ベンチ）はユーザーとエージェントが状態を変える対話シミュレーションを評価する。共通するのは、問題を集めるだけでなく、**何を満たせば成功かを先に定義し、問題の品質と採点方法を確かめる**点である。

第4回の宿題では、60候補すべてを実装するのではなく、自分のエージェントが担う機能から10件を選び、次を明記するのが実用的。

1. 質問が試す機能とケースの分類
2. 参照する用語集・講義資料
3. 期待する回答に必要な要件と、してはいけないこと
4. それを人・LLM・コード・状態検証のどれで採点するか

10件では1件の判定が全体の10ポイントに相当する。したがって、率だけで結論を出さず、件数・基準別の不一致・`unsure`・coverageも一緒に記録する。複数ターン、ツール実行、ファイル書き込みのような動作は、現在の宿題用評価処理だけでは十分に測れないため、別の対話・統合テストに分ける。

## 調査対象と読み方

候補一覧は [`implementation_cases.md`](./implementation_cases.md)、宿題の手順と評価の狙いは [`problem.md`](../problem.md)、既存結果の例は [`answer.md`](../answer.md) と [`lec04_cases.jsonl`](../../../data/eval/lec04_cases.jsonl) で確認した。入力画面は [`annotate.py`](../../../tools/annotate.py)、採点と回答生成は [`judge.py`](../../../app/judge.py)、採点基準は [`rubric.md`](../../../data/eval/rubric.md) を参照した。

外部情報は、ベンチマークの論文・公式リポジトリ・公式データセットページを優先した。添付画像の個別問題文は転載せず、記載されたベンチマークの説明と作成・検証方法を調べた。確認できた事実と、宿題への応用提案は分けて記す。

## 添付画像のベンチマークから確認できたこと

| ベンチマーク | 主に測るもの | 作成・検証、採点の特徴 | 宿題に活かせる点 |
|---|---|---|---|
| SWE-bench Verified | GitHub issueに対するコード修正 | 人が解決可能性を確認した500件。提出パッチを実際の環境に適用し、テストで評価する | 実際の利用に近い入力を使い、できれば成功条件を機械的に確かめる |
| GPQA Diamond | 大学院レベルの科学知識 | 専門家が問題と解説を作り、専門家レビュー、作問者による改訂、別の専門家レビューを経る。異分野の高技能者にも難度を確認 | 期待値だけでなく、なぜ正しいか・どんな誤解が起きるかを確認する |
| Humanity’s Last Exam | 多分野の閉じた知識問題 | 専門家の投稿をモデルで事前選別し、専門家レビューと採否判定を行う。正解の照合が可能な問題を重視 | 期待する答えを明確にし、問題の曖昧さと採点可能性をレビューする |
| τ²-bench | ユーザーとエージェントの対話・協調 | 状態を持つ環境で、初期状態・タスク・成功を表す条件を組み合わせる。対話後の状態も確認する | 発話だけではなく、複数ターンやツール操作の結果を別テストで確認する |

### SWE-bench Verified

**確認できた事実：** 元のSWE-benchは実際のGitHub issueを課題にし、モデルが作ったパッチをリポジトリに適用してテストするベンチマークである。元論文は12のPythonリポジトリから2,294件を収集したと説明する。Verifiedは、実際のソフトウェア開発者が解決可能性を確認した500件のサブセットで、公式リポジトリとHugging Faceの公式データセット表示でも500件を確認できる。評価は回答文の印象ではなく、実行環境でパッチがテストを通るかを調べる。

**画像の記載に関する注意：** 画像の「93人の開発者」「各課題を3名で確認」という内訳は、リンク先として示されているOpenAIの発表ページに関係する記載と読める。ただし、調査時にそのページは403で取得できず、参照できたSWE-bench公式README・評価ガイド・データセットページだけでは人数と割当数を照合できなかった。よって、ここでは「500件を実開発者が解決可能と確認した」ことまでを確認済みの事実として扱い、93人・3名の内訳は未確認事項とする。

**宿題への応用：** 自由記述の回答を「もっともらしいか」だけで評価するのではなく、可能な範囲で観察可能な条件にする。例えば「第5回の要点データがないと伝え、内容を作らない」は、参照データを確認したうえで、回答に創作がないかを確認できる。一方、実行環境を伴うコード修正ベンチマークの重さを、10件の会話評価セットに持ち込む必要はない。

### GPQA Diamond

**確認できた事実：** GPQA論文が報告する全体（main set）は448問の選択式問題で、GPQA Diamondはそのうち198問の部分集合である。Diamondはおおむね、2名の専門家が合意し、非専門家の正答が少ない問題を選ぶ条件で構成される。論文の作問手順では、専門家が問題・正解・解説を書き、同分野の専門家が回答してフィードバックし、作問者が改訂した後、別の専門家が再確認する。さらに、異分野の高技能者3名がWeb検索を利用して問題の難しさを確かめる。正解だけでなく、正解の理由と、誤答選択肢がなぜもっともらしく誤りなのかも説明させている。

**注意点：** 「Google-proof」は、論文の実験条件で非専門家の正答率が低かったという意味であり、検索すれば絶対に解けないという保証ではない。Diamondも全448問と同義ではなく、明示された選別条件による部分集合である。また、データセット配布元は問題例の公開転載を避けるよう求めているため、調査レポートや宿題回答には問題文をコピーせず要約を使う。

**宿題への応用：** 用語や講義内容の問題でも、作問者自身が「この質問に対する期待回答」を書き、曖昧な語や複数の正しい言い方を確認する。難易度を上げることより、正誤を判定できる質問にすることが重要。候補の「誤った前提」「関連用語」「範囲外と講座内の混在」では、何を訂正し、どこまで答えれば合格かもあらかじめ記す。

### Humanity’s Last Exam（HLE）

**確認できた事実：** 2026年11月13日時点で参照した論文v12（2026年10月19日改訂）は、100を超える分野の2,500問を報告している。専門家からの投稿を複数の高性能モデルで事前に試し、解けない問題を人手レビューへ回す。初期レビューでは大学院レベルのレビュアーがフィードバックし、各問に1〜3件のレビューを受けた後、主催者・専門家が採否を決定する。問題には正解と解説が必要で、曖昧さが少なく、正解を確認しやすい形式を重視する。論文の版によって記述が変わり、v1では3,000問、後の版では2,500問とされているため、件数を引用するときは版を明記する。

**宿題への応用：** 問題を用意したあとに、自分のエージェントの回答を見て期待値を後付けで決めるのではなく、質問作成時点で期待値・根拠・許容する言い換えを定める。レビュー時は「質問に複数の正解があり得ないか」「期待するふるまいが実際に確認できるか」を見る。また公開した10件を繰り返し調整すると、その10件への過適合が起きる。結果は今回のケースに対する診断とし、未使用の質問でも確認しない限り一般化しない。

### τ²-bench

**確認できた事実：** 2025年6月提出の論文は、電話会社のサポートを例に、エージェントだけでなくユーザー役もツールで環境の状態を変える「dual-control」を提案している。課題は、初期状態・解決手順・最終状態を検査するassertionなどの小さな部品を組み合わせて生成し、状態や手順数で難しさを制御する。会話後の状態を確かめられるため、適切な説明だけでなく、協調して正しい操作に到達したかを評価できる。論文は独立試行を繰り返し、成功率の揺れも分析している。

**名称と版の注意：** τ²-bench論文の方式と、現行の`sierra-research/tau2-bench`リポジトリの最新機能は同一とは限らない。現行READMEは後続版や多言語・音声機能も案内し、1.xと2.0の一部スコアは入力が同一でないため比較不可と注意している。画像や課題で説明するときは、τ-bench、τ²-bench、リポジトリの現行版を区別する。

**宿題への応用：** この宿題の`judge.py`は質問を1件ずつ独立に採点し、会話履歴やツール呼び出し結果を通常の採点対象にしない。したがって「承認を得てから保存したか」「曖昧さを確認して次のターンで解決したか」は、単一回答の採点で代用せず、状態を隔離した統合テストや対話テストに分ける。

## 作問候補を整理するための分類

この節以降では、**調査で確認した事実**と、そこから作問候補・宿題に対して導いた**提案**を分けて説明する。以下の分類はベンチマーク論文に共通して載っている公式分類ではない。前節までの4つの事例と、このリポジトリの60候補を対応づけて作った整理方法である。

### 分類の軸と、その根拠

| 分類軸 | 候補一覧で見る箇所 | 調査で確認した事実 | この軸を置く理由 |
|---|---|---|---|
| 利用者の目的・エージェントの機能 | 正常系の用語検索、講義要約、クイズ、学習支援、保存など | GPQA/HLEは閉じた知識問題、SWE-benchはコード修正、τ²-benchは対話と環境操作を課題にする。課題の種類によって成功条件も違う（[GPQA](https://arxiv.org/abs/2311.12022)、[HLE](https://arxiv.org/abs/2501.14249v12)、[SWE-bench](https://github.com/SWE-bench/SWE-bench)、[τ²-bench](https://arxiv.org/abs/2506.07982)） | ベンチマークごとに測る仕事が違うため、自分のエージェントにない機能を評価セットへ無理に入れない |
| 入力の条件・難しさ | 曖昧さ、欠落情報、誤った前提、複数依頼、指示の衝突など | GPQAは専門家の回答・フィードバックを受けて問題を改訂し、HLEはモデルによる事前確認と複数段階のレビューを行う（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.2](https://arxiv.org/html/2501.14249v12#S3.SS2)） | 入力が曖昧な問題と、情報がない問題と、矛盾した依頼を別の失敗要因として数えられる |
| 成功条件・判定方法 | 期待する回答、コード判定、LLM／人手判定、対話・状態の検査 | SWE-benchはパッチを実環境でテストし、GPQA/HLEは正解・解説のある問題を使い、τ²-benchは対話後の状態をassertion（期待状態かを確認する条件）で検査する（[SWE-bench README](https://github.com/SWE-bench/SWE-bench)、[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.1](https://arxiv.org/html/2501.14249v12#S3.SS1)、[τ²-bench §3.2](https://arxiv.org/html/2506.07982v1#S3.SS2)） | 回答文を読むだけで測れるのか、実際のツール・ファイル・会話状態を観察する必要があるのかを先に分ける |

### 60候補の各グループを、調査結果に結びつける

表の「根拠」は前節の研究で確認した内容、「宿題への提案」はこの課題向けに導いた方法である。ベンチマークで直接扱われていないグループは、そのことも明記した。

| 候補のグループ・番号 | 調査結果とのつながり（根拠） | そこから導く作問・採点の提案 |
|---|---|---|
| 正常系：講義資料の要約・整理（01–05、14） | GPQA/HLEは、問題の答えや根拠が確認できる閉じた課題を設計する（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.1](https://arxiv.org/html/2501.14249v12#S3.SS1)） | 質問で対象回を特定し、参照要点と回答に必要な要素を先に書く。要約の言い回しを固定せず、含むべき情報で評価する |
| 正常系：用語の検索・説明・関連づけ（06–12、25–26、28–29） | GPQA/HLEの問題には正解・解説があり、作問内容をレビューして正誤を確認する（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.1–3.2](https://arxiv.org/html/2501.14249v12#S3.SS1)）。ただし、これらは用語検索ベンチマークではない | この候補では同じ考え方を用語集に応用し、参照する用語IDと定義に沿った期待内容を記録する。検索精度そのものを測るには、別名・表記ゆれなど検索条件も明示する |
| 正常系：用語集と講義資料の照合（13） | 調査した4ベンチマークに、この講座のように2つの資料源を照合する直接の例はない | 講義資料と用語集がそれぞれ支える情報を分けて記録し、片方からもう片方の内容を推測していないか確認する。これは候補の性質に基づく提案 |
| 正常系：クイズ生成（15–18、22） | GPQAは選択肢・正解・誤答の理由を含む問題を作り、HLEも選択式と短答式を使う（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.1](https://arxiv.org/html/2501.14249v12#S3.SS1)）。ただし、評価問題を作ることと、エージェントがその場でクイズを生成することは別の課題 | 出題対象の回、問題数、形式、正解を見せるかを質問ごとに明記する。出題内容がランダムなら、固定の問題文との一致ではなく、回・形式・正解の妥当性を評価する |
| 正常系：回答形式・学習支援（19–21、23–24、27） | HLEは選択式と短答式を使い、GPQAは選択肢と正解・解説を用意する（[HLE §3.1](https://arxiv.org/html/2501.14249v12#S3.SS1)、[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)） | 件数・言語・形式などの機械的な条件と、ヒントの適切さなど意味の条件を分ける。前者はコードで判定できる場合があり、後者は参照付きルーブリックや人手確認が必要 |
| 正常系：書き込みを伴わない依頼（30） | τ²-benchは会話とツールを通じた環境操作を扱う（[τ²-bench §3](https://arxiv.org/html/2506.07982v1#S3)）。最終回答だけでは、ツールを呼んだかどうか分からないという点が参考になる | 「保存しない」依頼は回答文だけでなく、ツール呼び出しがないことも確認する。ただし、現在の`judge.py`はツールトレースを採点入力にしないため、別のログ・統合テストで確かめる |
| 境界系：質問の特定・文脈不足（01–02、07、16、30） | GPQA/HLEは問題の正確さ・一意性をレビューし、τ²-benchは複数ターンの対話を課題にする（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.2](https://arxiv.org/html/2501.14249v12#S3.SS2)、[τ²-bench](https://arxiv.org/abs/2506.07982)） | 何が不足していると確認質問が必要なのかを期待値に書く。確認後の解決まで評価したい場合は、質問1件ずつの評価ではなく、履歴付き対話テストにする |
| 境界系：回・データの指定不備（03–06、09、28） | 4ベンチマークに「講義回が欠番」という直接の分類はない。SWE-bench Verifiedが解決可能性を確認した部分集合を作った事実からは、課題の前提条件を確認する重要性を参考にできる（[SWE-bench README](https://github.com/SWE-bench/SWE-bench)） | 「講座に存在しない回」と「回は存在するが要点データがない」を分けてテストする。存在範囲と実際のデータ有無をそれぞれ参照して、期待値に記す |
| 境界系：根拠不足・誤った前提（08、10–11、19） | GPQA/HLEは正解と解説を用意し、問題の正確さや曖昧さをレビューする（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.1–3.2](https://arxiv.org/html/2501.14249v12#S3.SS1)） | 正しい部分・誤った前提・資料から分からない部分を分けて期待値に記す。「分からない」と「誤りを訂正する」をひとまとめに採点しない |
| 境界系：指示の衝突・過大な依頼（12–15） | 4ベンチマークの調査から、相反する出力指示をどう処理するかの直接の採点法は確認できなかった | これは候補一覧から作った独自のテスト分類。矛盾を指摘する、優先条件を尋ねる、可能な範囲で回答するなど、許容する応答を先に決めてから採点する |
| 境界系：複合・複数言語の依頼（17–18、24） | τ²-benchはユーザーとのコミュニケーションとタスク解決を一体で評価する（[τ²-bench](https://arxiv.org/abs/2506.07982)）。ただし、ここの複数言語・講座内外の組み合わせを直接検証しているわけではない | まず各要件を単独ケースで確認し、次に複合ケースを置く。複合ケースには依頼の各部分ごとの期待値を列挙し、部分回答も評価できるようにする |
| 境界系：指示の埋め込み・秘密情報（20–23） | 今回調べた4ベンチマークは、この候補群の安全ポリシーを定義する根拠ではない。講座の現行ルーブリックは「役割を変えさせる要求を断る」ことを範囲基準に含めている（[rubric.md](../../../data/eval/rubric.md)） | エージェントに適用する安全要件を先に決め、引用文・貼り付け文中の指示と利用者の依頼を区別する。実在する秘密情報は入力に入れない |
| 境界系：承認・ファイル操作（25–27） | τ²-benchの環境状態をassertionで確認する方法は、状態変更を評価する際の類例になる（[τ²-bench §3.2](https://arxiv.org/html/2506.07982v1#S3.SS2)）。承認の具体的な扱いは、このベンチマークから直接導かれるものではなく、講座エージェントの設計要件による | 承認前後の状態、実際のツール呼び出し、パス外書き込みや上書きの有無を、一時ディレクトリ等の隔離環境で検査する。回答文だけの採点とは別にする |
| 境界系：実行環境・ツール障害（29） | SWE-benchはテスト実行環境を使い、τ²-benchはシミュレーション環境を使う（[SWE-bench評価ガイド](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md)、[τ²-bench §3](https://arxiv.org/html/2506.07982v1#S3)） | 障害は質問文に書くだけでは発生しない。偽ツールやモックで例外・空結果を再現し、エラーを利用者へ伝えるか、根拠のない回答を作らないかを統合テストで見る |

## 調査結果から導いた、宿題用の10件の選び方

以下は論文やベンチマークが指定する配分ではなく、**この宿題の10件という上限**と、上表の分類から組み立てた一例である。括弧内は [`implementation_cases.md`](./implementation_cases.md) の候補番号。正常系・境界系で番号が重なるため、種類も併記する。

| 件数 | 選ぶケース | 例 | その枠を置く理由と根拠 |
|---:|---|---|---|
| 3 | 用語・講義要点の基本質問 | 正常系06、01、11 | 参照できる答えのある通常ケースを置き、根拠のある説明を確かめる（GPQA/HLEの正解・解説の考え方を、講義資料に応用） |
| 2 | エージェントの機能・出力指定 | 正常系15、21 | クイズ生成や指定形式など、実際に使う機能を確認する。形式の指定は意味の正しさと分けて見る |
| 2 | 情報の欠落・前提の誤り | 境界系03、08 | 欠落情報を作らないことと、誤った前提を訂正することは別の失敗要因なので、別々に置く |
| 2 | 曖昧さ・複合依頼 | 境界系01、24 | 確認質問が必要な状況と、回答可能な部分／範囲外部分を分ける状況を確かめる |
| 1 | 安全・範囲の境界 | 境界系21など | エージェントの範囲・安全要件を確認する。期待する安全方針はベンチマークから借りず、自分のエージェントの要件に基づいて決める |

保存などの副作用がある機能を持つ場合も、10件の回答評価に無理に混ぜる必要はない。τ²-benchが示すように、状態の変化を評価したいなら、期待する状態を設定し、実行後の状態を別の統合テストで検査するのが適切である。この10件配分は説明用の出発点であり、実装していない機能は自分のエージェントの別機能に置き換える。

## 宿題の手順に沿った実装ヒントと根拠

| 宿題で行うこと | 調査・リポジトリで確認した根拠 | そこからの具体的な進め方 |
|---|---|---|
| 1. 10件を選ぶ | 課題は自分のエージェントについて質問・期待行動を10件作るもの（[problem.md](../problem.md)）。4ベンチマークはそれぞれ異なる仕事を評価する | [`implementation_cases.md`](./implementation_cases.md)から、自分の機能に対応する通常ケースと重要な境界ケースを選ぶ。候補の全グループを網羅したと主張しない |
| 2. 質問と参照を記入する | GPQAは問題・正解・説明を用意しレビューする。HLEも答えと解説を提出要件に含める（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.1](https://arxiv.org/html/2501.14249v12#S3.SS1)）。入力画面は質問・種類・期待値・用語集IDを保存する（[annotate.py](../../../tools/annotate.py)） | 回答を生成する前に「何を参照し、何を満たせば合格か」を書く。期待値は答えの丸写しでなく、判定できる条件にする |
| 3. 問題と期待値を点検する | GPQAは専門家のフィードバック後に改訂し、別の専門家が再確認する。HLEも複数段階のレビューを行う（[GPQA §2.1](https://arxiv.org/html/2311.12022v1#S2.SS1)、[HLE §3.2](https://arxiv.org/html/2501.14249v12#S3.SS2)） | 宿題では同じ規模のレビューは不要。可能なら別の人に数件を読んでもらい、「質問の意味が一つに定まるか」「期待値を回答から判定できるか」を試す。これは研究手法を小規模に応用した提案 |
| 4. 回答を生成し、採点する | `--generate`は評価セット内の質問をエージェントへ1件ずつ渡す。`judge_prompt`には質問・回答・参照を渡し、4基準をLLM、回表示をコードで採点する（[judge.py](../../../app/judge.py)） | ランダムに生成されるクイズは特定の問題文と照合せず、出題対象・形式・正解の妥当性を見る。文字数等の一意な条件だけコード判定に向ける |
| 5. 結果を解釈し、基準を直す | 課題は基準別一致率、unsure、coverageを確認し、基準を1か所ずつ変更する手順を示す（[problem.md](../problem.md)）。HLEは論文版・採点方法を明記し、SWE-benchも再現できる環境でテストを行う | モデル名、評価セット、ルーブリック、実行時点を記録する。10件では1件が10%に当たるので、生の件数と不一致例を併記し、一般性能の証明とはしない |
| 6. 状態変化や複数ターンを評価する | τ²-benchは対話後の環境状態をassertionで検査する（[τ²-bench §3.2](https://arxiv.org/html/2506.07982v1#S3.SS2)）。一方、宿題の採点処理は各ケースを独立に処理する（[judge.py](../../../app/judge.py)） | 続きの質問、承認、ファイル保存、ツール選択はこの10件の回答採点だけで測ったことにしない。対話履歴・ツール記録・ファイル状態を確認する別テストにする |

## リポジトリの実装に当てはめるときの注意

ここはベンチマーク一般の主張ではなく、このリポジトリのコードを読んで確認した制約である。

- [`annotate.py`](../../../tools/annotate.py)の`category`は自由記入欄で、`question`、`expected`、用語集の参照IDと一緒に保存される。分類タグを使うだけなら、今回の調査を理由にスキーマや画面を変更する必要はない。
- [`judge.py`](../../../app/judge.py)の`reference_text`は用語集と期待するふるまいを採点プロンプトに加える。4つのLLM基準には同じ期待値が渡るため、期待値に異なる種類の条件を詰め込みすぎない。
- `judge_cases`は各ケースを個別に採点し、`lecture_mark`を回答末尾の「第N回」でコード判定する。回に結び付かない質問や講座外質問では、この一律判定が意図と合うか確認する。
- `generate_answers`は回答を同じ評価データへ書き戻す。生成前後を比較したい場合はコピーを残すか、別の評価ファイルを指定する。
- `--model test`は採点処理の動作確認用の規則ベース偽モデルであり、実際のLLM採点品質を測るものではない。
- 保存の承認やファイル状態の確認は、出力文を読むだけではできない。テスト用の一時場所を使うなど、実データへ影響しない隔離したテストで確認する。
