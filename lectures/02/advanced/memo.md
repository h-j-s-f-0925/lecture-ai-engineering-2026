# 第2回 宿題 発展 メモ：用語集を学習させて、検索と比べる

- この宿題では、講座の用語集をモデルに学習させ、用語の意味を答えられるようになるかをテストで確かめる。
- 同じテストを「学習前」「学習後」「用語集を検索して渡す」の 3 つの方式で行い、結果を比べる。
- 学習データはスクリプトが作る。自分で作るのは、テスト問題と採点の基準。

テスト問題とは、学習の効果を測るためにモデルに聞く質問の一覧のこと。学習データ（覚えさせる教材）とは別に用意し、学習前・学習後・検索ありの 3 つの方式で、同じ質問を同じように聞く。全部で 22 問あり、1 問は次の 3 つでできている。

| 1 問を作るもの | 例 |
|---|---|
| 質問の文 | 「LoRA」とは何ですか？ |
| 質問の種類 | 同じ文（8 問）・言い換え（8 問）・知らない語（6 問）のどれか（6 章） |
| 採点の基準 | 答えに「行列」と「固定」をすべて含めば正解（7 章） |

採点とは、モデルの答えが正解かどうかを、決めた基準でコードが ○× に分けること。人が答えを読んで判断するのではなく、答えの文字列に決めた語句が入っているかだけを見る。3 つの方式を同じ基準で採点するので、正解の数をそのまま比べられる。

| 質問の種類 | 採点の基準 | 例 |
|---|---|---|
| 同じ文・言い換え | `must_include` の語句を**すべて**含めば ○ | LoRA の質問なら「行列」と「固定」の両方 |
| 知らない語 | `must_any` の語句を**どれか 1 つ**含めば ○ | 「分かりません」「記載がありません」など |

語句が入っているかだけを見るので、語句を含むのに中身が間違っている答えや、語句を言い換えた正しい答えを見落とすことがある。そのため、採点のあとで答えの原文も読む（7 章、手順 5）。

テスト問題は `lectures/02/advanced/make_glossary_test.py` に書き、確かめてから `glossary_test.json` に書き出して Colab で使う（手順 2）。

## 1. 課題文と、この宿題で確かめること

課題文（`lectures/02/problem.md` の宿題の表の「発展」）は次のとおり。

> `scripts/make_sft_dataset.py` で講座の用語集から Q&A データ（`messages` 形式の JSONL）を作り、FAQ の代わりに学習させる。評価用の質問（用語集にある語・言い回しを変えた質問・用語集にない語）と正解を自分で用意し、学習前後を比べる。用語集を検索する仕組みと比較して、モデルを学習させる際のメリットとデメリットについて考察する

この宿題で答えを出したい問いは、次の 1 つ。

- 用語の意味を、**モデルに覚えさせる（学習）**のと、**聞かれたときに用語集から探して渡す（検索）**のとでは、何が違うか。

## 2. 演習・基礎・実装からの流れ：発展では、学習させる中身が変わる

- 演習・基礎・実装・発展は、どれも同じノートブック（`notebooks/lora_format_tuning.ipynb`）を使う。
- 演習が基準になる。基礎・実装・発展は、演習のどこか 1 か所を変えて、結果がどう変わるかを見る。
- 基礎と実装は、演習と同じ問い（答え方が学習で身につくか）を、条件を変えて確かめた。
- 発展は、学習させる中身を「答え方」から「知識」に変える。問いそのものが変わるので、ほかの 3 つより変わる部分が多い。

### 4 つの課題で変えるものと、確かめる問い

結果の列は、`lectures/02/answer.md` に書いた自分の結果から取った。

| 課題 | 演習から変えるもの | 確かめる問い | 自分の結果 |
|---|---|---|---|
| 演習 | 何も変えない（基準） | LoRA で学習すると、何が変わり、何が変わらないか | `format_rate` 9.52% → 100%、`content_rate` 0% → 90.48%。根拠なしの 2 問で断定が残った |
| 基礎 | 設定を 1 つ（学習率 `lr` を 2e-4 → 1e-4） | 設定を変えると、結果はどう変わるか | 正解率は同じ 90.48%。最終 loss は 0.0138 → 0.0326 に上がり、間違えた質問が入れ替わった |
| 実装 | 題材（`FAQ` と質問を、講座リポジトリのコマンド FAQ に） | 自分で選んだ題材でも、同じことが起きるか | `content_rate` は 71.43%。FAQ の語を含む根拠なしの質問で、FAQ の別の項目の文を写して断定した |
| 発展 | 学習させる中身（答え方 → 知識） | 知識を学習で入れると、検索で渡すのと比べて何が違うか | これから |

- `format_rate`（形式遵守率）は、JSON の形式を守れた質問の割合。
- `content_rate`（内容正解率）は、`needs_review` と必須語句が正解と合った質問の割合。

### 発展でも変えないもの

- モデル（`Qwen/Qwen3.5-0.8B`）と、LoRA の設定（`lora_r=16`、`lora_alpha=32`、`lr=2e-4`）。
- 生成の設定のうち、毎回いちばん確率の高い語を選ぶ貪欲生成（`do_sample: False`）。同じ質問には毎回同じ答えが出るので、前後を比べられる。
- 学習の前後で、同じテスト問題を同じ採点で比べること。
- 必須語句が答えに含まれるかで、内容を採点する考え方。

### 発展で変わるもの

| 項目 | 演習・基礎・実装 | 発展 |
|---|---|---|
| モデルに渡す入力 | system ＋ FAQ の全文 ＋ 質問 | 質問だけ（3 章で実例を示す） |
| 正解の出力 | `{"answer": ..., "needs_review": ...}` の JSON 1 行 | 用語集の定義文 |
| 学習データ | 14 件（ノートブックに手書き） | 130 行（スクリプトが作る） |
| エポック数 | 20 | 5 から始め、足りなければ 10（データが約 9 倍になるため。手順 0） |
| 採点 | `format_rate` と `content_rate` | 質問の 3 種類（同じ文・言い換え・知らない語）ごとの正解率（JSON ではないので `format_rate` は使わない） |
| 根拠が無い質問の扱い | `needs_review: true` と「確認が必要」と答える例を学習する | 学習データに無い。テストの「知らない語の質問」で確かめるだけ |
| 比べる相手 | 学習前と学習後の 2 つ | 学習前・学習後・検索ありの 3 つ |

### 基礎と実装で分かったことを、発展の設計に使う

1. 実装では、モデルが知らない題材を選んだ。知っている題材だと、FAQ を読んで答えたのか、もともとの知識で答えたのか区別できないから。
   - 発展でも同じ理由で、テストの語は講座に固有の語を中心にする（8 章の約束 4）。
2. 実装では、必須語句をその項目の文にしか出てこない語にした。別の項目の文で答えても正解になるのを防ぐため。
   - 発展でも、ほかの語の定義に出てくる語は必須語句にしない（7 章）。
3. 実装では、学習後に、FAQ の別の項目の文を写して答える失敗が出た（例：「--trace の出力をファイルに保存できますか」に、`--trace` の項目の文で答えた）。
   - 発展では、これが「別の語の定義で答える」取り違えとして出る可能性がある（7 章の間違え方の表）。
4. 実装では、学習前に「確認が必要です」と答えていた 3 問が、学習後に断定に変わった。学習で「FAQ の文を写す」答え方を強く覚えたためだと考えた。
   - 発展の学習データは、130 行すべてが定義を言い切る例で、「知らない」と答える例は 0 件。実装よりもさらに、知らない語で言い切るようになると予想できる（6 章）。
5. 基礎では、最終 loss が上がっても正解率は変わらず、間違えた質問が入れ替わった。
   - 発展でも、正解率の数字だけでなく、答えの実例を読んで間違え方を確かめる。
6. 基礎と実装の考察で、「形式はファインチューニングで整え、根拠は検索で取得するのがよい」と書いた。ただし、検索を実際には試していないので、これは予想だった。
   - 発展では、検索ありの方式を実際に用意し、この予想を数字で確かめる。発展の考察は、基礎と実装の考察の答え合わせになる。

## 3. 演習との一番の違い：答えの資料をモデルに見せない

### 演習では、FAQ を毎回プロンプトに入れていた

演習のノートブックでモデルに渡していた入力と、正解の出力は次のとおり（セクション 3 の `build_messages` が作る）。

```text
[system] あなたは講座 FAQ の回答係です。与えられた FAQ だけを根拠に、必ず JSON 1 行で答えてください。…
[user]   FAQ:
         - 課題の提出期限は 9 月 30 日 23:59（日本時間）です。
         - 提出先は学習ポータルの「課題」欄です。
         - …（5 項目すべて）

         質問: 課題の提出期限はいつですか
[正解]   {"answer": "課題の提出期限は 9 月 30 日 23:59（日本時間）です。", "needs_review": false}
```

- モデルは、目の前の FAQ を見ながら答える。
- 学習で身につけたのは、「JSON 1 行で答える」「FAQ に無いことは『確認が必要』と書く」という**答え方**。
- 答えの中身（提出期限など）は、毎回 FAQ に書いてあるので、覚える必要がない。

### 発展では、質問だけを渡す

発展の学習データ（スクリプトが作る）は、次の形になる。

```text
[user]   「lecNN-start タグ」とは何ですか？
[正解]   AIE2026の講座repoで、各回の演習開始時点のコードに付けているGitタグ（例：lec03-start）。前の回が終わっていなくても、このタグからブランチを作ればその回の演習を始められる。
```

- system メッセージも、FAQ も無い。モデルに渡るのは質問だけ。
- 正解は JSON ではなく、用語集の定義文そのもの。
- モデルは、学習で覚えた内容だけを頼りに答えることになる。

課題文の「FAQ の代わりに学習させる」は、**資料（用語集）を見せる代わりに、資料の中身を覚えさせる**という意味になる。

### 試験にたとえると

- 演習は、教科書の持ち込みが許された試験にあたる。答え方の練習だけをすればよい。
- 発展の学習方式は、持ち込みできない試験にあたる。教科書の中身を事前に暗記して臨む。
- 検索方式は、試験中に索引で該当ページを探して、そのページだけを開いてよい試験にあたる。

たとえの限界として、モデルは定義文をそのまま覚えるとは限らない。覚えた内容と、もともと知っている一般的な知識を混ぜて、文を作ることがある。

## 4. 3 つの方式を比べる

| 方式 | 用語の意味はどこにあるか | モデルに渡す入力 | 準備すること |
|---|---|---|---|
| 学習前 | どこにも無い（事前学習で知った一般的な知識だけ） | 質問だけ | なし |
| 学習後 | モデルの重み（LoRA で学習した adapter） | 質問だけ | LoRA 学習（T4 で数分） |
| 検索あり | プロンプト | 探した定義 ＋ 質問 | 用語集から語を探す仕組み |

- 重みは、モデルの中にある大量の数値のこと。学習は、この数値を少しずつ変えて、正解の出力が出やすくなるようにする作業。
- adapter（アダプター）は、LoRA で学習した小さな追加の重み。元の重みは変えずに、これを足して使う。
- 検索ありは、課題文の「用語集を検索する仕組み」にあたる。第 5 回で扱う RAG（Retrieval-Augmented Generation、検索拡張生成）の簡単な版。
  - 検索の仕組みは自分で作らず、講座のリポジトリにある `search_glossary`（`app/tools.py`）を使う。第 3 回でエージェントのツールとして、第 6 回で MCP サーバーとして使っている、講座の用語集の検索そのもの。
  - 検索は手元で 1 回だけ実行し、22 問ぶんの検索結果をファイルにしておく（手順 2-7）。Colab では、その検索結果を質問の前に入れて渡すだけ。
  - 学習はしない。学習前のモデルに、答えの資料を渡すだけ。

学習前は、比べるための基準になる。学習後と検索ありが、学習前からどれだけ良くなったかを見る。

## 5. 用意するものの全体像

| 用意するもの | 何か | 作り方 |
|---|---|---|
| 学習データ `glossary_sft.jsonl` | 「質問 → 定義文」の組を 1 行に 1 つ書いたファイル | スクリプトが作る |
| テスト問題（`test`） | 学習の前後で同じように聞く質問の一覧 | **自分で作る** |
| 採点の基準（`gold`） | 質問ごとに「どんな答えなら正解か」の条件 | **自分で作る** |
| 検索結果 | 22 問それぞれを講座の `search_glossary` で検索した結果 | 講座の検索をそのまま使う（作らない） |

### 学習データは、スクリプトが 130 行作る

`scripts/make_sft_dataset.py` の中心は、次の部分。

```python
# 質問の言い回しのひな形を 2 つ用意する
TEMPLATES = ["「{term}」とは何ですか？", "{term}について簡単に説明してください。"]
...
# 用語集の語を 1 つずつ取り出す
for t in terms:
    # 1 つの語に、2 つのひな形をそれぞれ当てはめる
    for template in TEMPLATES:
        # 質問（user）と、正解の定義文（assistant）の組を作る
        record = {
            "messages": [
                {"role": "user", "content": template.format(term=t["term"])},
                {"role": "assistant", "content": t["definition"]},
            ]
        }
        # 1 組を JSON 1 行として出力する
        sys.stdout.write(json.dumps(record, ensure_ascii=False) + "\n")
```

- 用語集（`data/glossary.json`）には 65 語ある。1 語につき 2 行なので、65 × 2 = 130 行になる。
- 実際に動かして、130 行になることを確かめた。
- JSONL（JSON Lines）は、1 行に JSON を 1 つずつ書いたファイルの形式。

### 演習の部品との対応

演習のノートブックのセクション 2 で手書きされていた部品が、発展では次のものに置き換わる。

| 演習の部品 | 演習での中身 | 発展での対応物 |
|---|---|---|
| `FAQ` | 正解の文 5 つ | 用語集の定義文 65 個 |
| `GROUNDED` の質問 | 学習用の言い回し | スクリプトの `TEMPLATES`（2 つ） |
| `GROUNDED` の必須語句 | 正解に含むべき語 | 語ごとの必須語句（**自分で作る**） |
| `TEST_EXTRA_GROUNDED` | テスト専用の言い換え | 言い回しを変えた質問（**自分で作る**） |
| `UNGROUNDED` | FAQ に無い質問 | 用語集にない語の質問（**自分で作る**） |
| `test` / `gold` | テスト問題と採点の基準 | 3 種類の質問と採点の基準（**自分で作る**） |

課題文の「評価用の質問と正解を自分で用意」は、表の「自分で作る」のところを指す。学習データはスクリプトが作るが、テストの物差しはどこにも無いので、自分で作る。

## 6. テスト問題の 3 種類

テスト問題は、学習データとの関係で 3 種類に分ける。この先は、次の呼び名で呼ぶ。

| 呼び名 | 語を学習したか | 質問の文を学習したか | 確かめること |
|---|---|---|---|
| 同じ文の質問 | した | した（学習データとまったく同じ文） | 覚えたか |
| 言い換えの質問 | した | していない（初めて見る文） | 使える知識になったか |
| 知らない語の質問 | していない（用語集に無い） | していない | 知らないと言えるか |

### 同じ文の質問は、覚えたかを見る

- 例：「「宿題の3レベル」とは何ですか？」
- 学習データとまったく同じ文で聞く。
- 練習問題と同じ問題を試験に出すのと同じで、暗記できたかが分かる。

### 言い換えの質問は、使える知識になったかを見る

- 例：「AIE2026 の宿題レベルには何がありますか？」
  - 「宿題レベル」は、「宿題の3レベル」の別名（用語集の `aliases`）。
- 語は学習済みだが、質問の文は初めて見る形にする。
- 同じ文の質問で正解して、言い換えの質問で間違えたら、「この文が来たらこの答え」という丸暗記をしただけで、知識としては使えていない、と分かる。

### 知らない語の質問は、知らないと言えるかを見る

- 例：「「lecNN-end タグ」とは何ですか？」
  - 用語集には「lecNN-start タグ」はあるが、「lecNN-end」という語は用語名（`term`）・別名（`aliases`）・定義（`definition`）のどこにも無いことを確かめた（手順 2-7）。
- 講座に関係がありそうで、用語集に無い語を選ぶ。もっともらしい作り話をするかが、はっきり分かるため。
- 正しい答えは「分かりません」「用語集にありません」のように、知らないと答えること。

### 結果の組み合わせから分かること

| 同じ文 | 言い換え | 知らない語 | 分かること |
|---|---|---|---|
| ○ | ○ | ○ | 用語の意味を覚え、知らない語には知らないと言える（理想） |
| ○ | × | — | 丸暗記。質問の文が変わると答えられない |
| ○ | ○ | × | 意味は覚えたが、知らない語にも定義らしい文を作ってしまう |
| × | × | — | 学習が足りない。エポック数や学習率を見直す |

### 知らない語の質問は、学習後に悪くなると予想できる

- 学習データの 130 行は、すべて「用語を聞かれたら、定義を言い切る」例になっている。
- 「知りません」と答える例は 1 行も無い。
- そのため、学習後は、知らない語でも言い切る癖が強まると予想できる。
- 演習で確かめた「形式は学習で身につくが、知らないことへの判断は保証されない」の、知識の版にあたる。予想どおりになるかを確かめるのが、この宿題の見どころの 1 つ。

## 7. 採点のしかた

### 同じ文と言い換えの質問は、必須語句をすべて含めば正解にする

- 答えは自由な文章なので、定義文と一字一句同じにはならない。
- 演習の `check_content` と同じように、「答えに必須語句がすべて含まれるか」で判定する。
- 例えば「宿題の3レベル」の必須語句は「基礎」「実装」「発展」の 3 つ。3 つそろえば、講座の定義で答えたと言える。
- 8 語すべての必須語句は、手順 2-2 の表にまとめた。

必須語句を選ぶときの注意は 3 つ。

1. 必須語句の組を全部含む定義が、ほかの語に無いようにする。
   - 例えば「AIE2026」は、宿題の3レベル・answer.md・lecNN-start タグ・既定モデルの定義すべてに出てくる。必須語句にすると、別の語の定義を答えても正解になってしまう。
   - 1 語ずつならほかの定義に出てきてもよい。組にしたときに、その語の定義にしか全部そろわなければよい。例えば answer.md の「PR」は、プルリクエストの定義にも出てくる。しかし「lectures」と組にすれば、全部そろうのは answer.md の定義だけになる。
2. 一般的な意味を答えても出てくる語だけにしない。
   - 例えば既定モデルの必須語句を「モデル」にすると、講座の定義を知らなくても正解になる。
3. 答えが途中で切れないようにする。
   - 答えが長いと、`max_new_tokens`（1 回に生成する最大のトークン数）に達して、途中で切れることがある。
   - 必須語句が定義の後ろのほうにあると、知識があっても、長さのせいで不正解になってしまう。
   - そのため、手順 3 で `max_new_tokens` を、いちばん長い定義（212 文字）が収まる大きさにする。

### 知らない語の質問は、「知らない」を表す語句のどれかを含めば正解にする

- 「分かりません」「わかりません」「知りません」「記載がありません」「情報がありません」「確認が必要」のどれか 1 つが入っていれば正解にする。
- 同じ文と言い換えの質問は「すべて含む」で判定するが、知らない語の質問は「どれか 1 つを含む」で判定する点が違う。
- 「ありません」だけを語句にはしない。作り話の答えの中の「〜ではありません」でも正解になってしまうため。

### 間違え方は 4 つの型に分けて見る

演習では、失敗を「断定」と「逃げ」に分けて見た。発展では次の 4 つで見る。

| 間違え方 | 起きやすい質問 | 例 |
|---|---|---|
| 作り話 | 知らない語 | 用語集にない語に、それらしい定義を作って答える |
| 取り違え | 同じ文・言い換え | 「開始タグ」を聞かれて、answer.md の定義を答える |
| 逃げ | 同じ文・言い換え | 学習した語なのに「分かりません」と答える |
| 一般論 | 同じ文・言い換え | 「既定モデル」を聞かれて、講座の定義ではなく一般的な意味を答える |

## 8. 守る約束

### 約束 1：言い換えと知らない語の質問を、学習データに入れない

- 言い換えの質問が学習データの文と同じになると、同じ文の質問と区別がなくなる。
- 知らない語が用語集に入っていると、「用語集にない語」にならない。
- 用語名だけでなく、別名（`aliases`）とも重なっていないかを確かめる。
  - 例えば「開始タグ」は `lecNN-start タグ` の別名なので、知らない語の質問には使えない。言い換えの質問の材料になる。
- 演習のノートブックの `assert len(set(all_questions)) == len(all_questions)` と同じように、重なりをコードで確かめる。

### 約束 2：同じ文の質問は、わざと学習データと同じ文にする

- 演習では、テストの質問を学習データからすべて分けていた。
- 発展の同じ文の質問は、暗記できたかを見るために、学習データと同じ文にする。演習とは逆なので注意する。

### 約束 3：3 つの方式で、同じテスト・同じ採点・同じ生成の設定を使う

- 変えるのは「用語の意味がどこにあるか」だけにする。
- テスト問題や生成の設定（`do_sample: False`、`max_new_tokens`）が方式ごとに違うと、差が出ても、何による差か分からなくなる。
- 検索ありの方式も、プロンプトに足すのは検索結果だけにし、「無ければ『知らない』と答えて」のような指示は足さない。
  - 指示を足すと、知らない語の質問で正解が増えても、検索の効果なのか指示の効果なのか分からなくなる。

### 約束 4：同じ文と言い換えの質問は、講座に固有の語を中心に選ぶ

- 用語集の 65 語には、一般的な用語と講座に固有の語がまざっている。
  - 一般的な用語の例：LoRA、temperature、トークン、過学習。
  - 講座に固有の語の例：宿題の3レベル、answer.md、lecNN-start タグ、既定モデル。
- 一般的な用語は、学習前のモデルも知っている可能性がある。学習前から正解すると、学習の効果が測れない。
- 実装レベルのメモの「モデルが知らない題材にする」と同じ考え方。
- 一般的な用語は、比べるために 2〜3 問だけ入れる。学習で講座の定義に寄るのかを見られる。

## 9. 手順

### 手順 0：方針を決める

| 決めること | 方針 | 理由 |
|---|---|---|
| 出力の形 | 定義文のまま（JSON にしない） | 課題文は、スクリプトの出力をそのまま学習に使う前提で書かれている |
| 学習する語 | 65 語すべて | 一部の語を学習から外すと 知らない語と同じ扱いになり、比べる軸が増えて読み取りにくくなる |
| 比べる方式 | 学習前・学習後・検索ありの 3 つ | 考察で問われているメリットとデメリットを、数字で示せる |
| 「知らない」と答える例を学習に入れるか | 1 回目は入れない | まず元のデータで何が起きるかを見る。結果を見て、2 回目で試すかを決める |
| エポック数 | 5 から始める。学習後に、同じ文の質問の正解が 8 問中 4 問未満なら、10 にして学習し直す | 学習データが演習の 14 件から 130 件に増えたので、演習の 20 のままだと約 340 ステップ・約 34 分かかる。5 なら約 85 ステップ・約 9 分（どちらも 1 ステップ約 6 秒からの見積もり）。ただし 1 つの語を学習する回数は 10 回（ひな形 2 つ × 5 周）で、演習の 1 件あたり 20 回より少ないので、足りなければ増やす。同じ文の質問にすら答えられないなら、言い換えや検索と比べる前に、学習が足りていない |

### 手順 1：学習データを作って確かめる（ローカル）

Git Bash で、リポジトリのルートから次を実行する。

```bash
# 標準出力の文字コードを UTF-8 にして、学習データをファイルに書き出す
PYTHONIOENCODING=utf-8 uv run python scripts/make_sft_dataset.py > lectures/02/advanced/glossary_sft.jsonl
# 行数を数える
wc -l lectures/02/advanced/glossary_sft.jsonl
```

- `130 lectures/02/advanced/glossary_sft.jsonl` と出れば成功。
- `PYTHONIOENCODING=utf-8` は必ず付ける。
  - `PYTHONIOENCODING` は、Python が画面やファイルへ文字を書き出すときの文字コードを決める環境変数。
  - Windows では、付けないと日本語が UTF-8 ではなく cp932（Windows の日本語の文字コード）で書き出される。実際に付けずに動かして、UTF-8 として読めないファイルになることを確かめた。
  - Colab は UTF-8 で読むので、cp932 のファイルは文字化けや読み込みエラーになる。
  - 課題文のとおり Codespaces（Linux）で実行する場合は、もともと UTF-8 なので付けなくてもよい。
- `glossary_sft.jsonl` は Colab にアップロードするファイル。どのデータで学習したかを残すため、`lectures/02/advanced/` に置いてコミットする。

| 2-2 | 語ごとに必須語句を決める | 同じ文・言い換えの採点の基準 |
| 2-3 | 同じ文の質問を作る | 8 問 |
| 2-4 | 言い換えの質問を作る | 8 問 |

同じ文の質問と言い換えの質問は、同じ 8 語を使う。同じ語を、学習と同じ文と違う文で聞くので、2 つの結果の差が「文が変わったこと」だけによるものになる。

#### 2-1 テストに使う語を 8 個選ぶ

1. 講座に固有の語を 6 個、一般的な用語を 2 個にする（8 章の約束 4）。
2. 定義の中に、その語にしか出てこない語句がある。必須語句にできるため。
3. 別名（`aliases`）がある。言い換えの質問を作りやすいため。

| 語（用語集の `id`） | 種類 | 別名 | 選んだ理由 |

#### 2-2 語ごとに必須語句を決める

選び方の注意は 7 章に書いた 3 つ。8 語の必須語句は次のとおり。

| 語 | 必須語句（すべて含めば正解） | この語句にした理由 |
|---|---|---|
| 宿題の3レベル | 「基礎」「実装」「発展」 | 3 つの段階を表す語がそろえば、講座の定義で答えたと言える |
| answer.md | 「lectures」「PR」 | ファイルの置き場所（`lectures/NN/answer.md`）と、提出のしかた（PR）が入る |
| lecNN-start タグ | 「タグ」「ブランチ」 | 「タグからブランチを作って始める」という講座での使い方が入る |
| 既定モデル | 「gemini-3.5-flash-lite」 | 一般的な意味を答えたら出てこない、講座に固有の値 |

#### 2-3 同じ文の質問を作る

- 学習データの 1 つ目のひな形「「{term}」とは何ですか？」の `{term}` に、用語集の用語名（`term` の値。例：「LoRA」）を入れるだけ。
  - 例：「「宿題の3レベル」とは何ですか？」
- 学習データとまったく同じ文になる。同じ文の質問は暗記を確かめるので、これでよい（8 章の約束 2）。
- 1 問だけ例外がある。「「lecNN-start タグ」とは何ですか？」は、用語名に必須語句の「タグ」が入っている。
  - 用語名は変えられないので、避けられない。
  - 「ブランチ」と組にしているので、質問の「タグ」を写しただけでは正解にならない。

#### 2-4 言い換えの質問を作る

言い換えの質問は、聞き方を 2 通りに分けて 4 問ずつ作る。

| 聞き方 | 作り方 | 例 |
|---|---|---|
| 別名で聞く（4 問） | 用語名の代わりに別名（`aliases` の値。例：「デフォルトモデル」）を使い、文の形もひな形と変える | 「この講座のデフォルトモデルは何ですか？」 |
| 用語名も別名も出さずに聞く（4 問） | 用語名も別名も使わず、定義の一部から聞く | 「前の回が終わっていなくても、次の回を始められる仕組みは何ですか？」（lecNN-start タグ） |

作るときの決まりは 3 つ。

1. 学習データの 2 つのひな形と、同じ形にしない。同じ形だと、別名を入れただけの、同じ文の質問に近くなる。
2. 必須語句を質問の文に入れない。質問を写すだけで正解になるのを防ぐため。
3. 答えが 1 つに決まる聞き方にする。実装では「第1回目の宿題で使用したコマンドは？」が、FAQ だけでは答えが 1 つに決まらない質問になってしまった。

2 通りに分けるのは、検索方式の弱点を測るため。講座の検索 `search_glossary` に質問の文をそのまま渡すと、2 つの聞き方で結果がはっきり分かれた（2-7 のコードで実行した結果）。

| 聞き方 | 質問 | 検索で見つかった語 |
|---|---|---|
| 別名で聞く | 4 問すべて（例：この講座のデフォルトモデルは何ですか？） | 正しい語（例：既定モデル） |
| 用語名も別名も出さずに聞く | AIE2026 で、各回の結果を書いて出すファイルは何ですか？ | 見つからない |
| 用語名も別名も出さずに聞く | 前の回が終わっていなくても、次の回を始められる仕組みは何ですか？ | 見つからない |
| 用語名も別名も出さずに聞く | 2026 年 10 月に 1.0 が公開された、最小構成のエージェントは何ですか？ | AIエージェント（間違い。AIエージェントの別名「エージェント」に一致した） |
| 用語名も別名も出さずに聞く | 本講座で、使う MCP サーバーを書いておくファイルはどれですか？ | MCP、MCPサーバー（間違い。用語名の「MCP」に一致した） |

- 学習方式は、用語名も別名も出さない質問でも、覚えた知識から答えられるかもしれない。
- 検索方式は、用語名か別名が一致しないと答えの資料を渡せない。
- この違いを、言い換えの質問の後半 4 問で比べられる。

#### 2-5 知らない語の質問を作る

- 用語集に無い語を 6 個作る。用語集の語に近い語を 3 個、遠い語を 3 個にする。
  - 近い語：「lecNN-end タグ」（lecNN-start タグに近い）、「question.md」（answer.md に近い）、「宿題の応用レベル」（宿題の3レベルに近い）。
  - 遠い語：「AIE2026の修了課題」「AIE2026の講座バッジ」「AIE2026の週次チェックイン」。
- 近い語は、知っている語の定義を流用して答えるかを見るため。実装で、FAQ の別の項目の文を写して断定した失敗と同じ型になる。
- 遠い語には「AIE2026の」を付ける。付けないと「修了課題」の一般的な意味を答えても正解に見えてしまい、作り話と区別できない。
- 質問の文は、同じ文の質問と同じひな形「「{term}」とは何ですか？」にする。
  - 文の形は学習で見慣れたものにして、違いを「語を知らない」ことだけにするため。
- 採点の基準は、7 章の「知らない」を表す語句のどれかを含むこと。
- 知らない語の質問の答えは、語句の判定だけでは外れやすい。例えば「確認が必要」と書いたあとに作り話を続けることもある。採点のあとで、答えの原文も読む。

#### 2-7 約束を守れているかを確かめ、検索結果を付けてファイルにする

2-1〜2-6 で作ったテスト問題に対して、1 つのコードで次の 3 つを行う。

1. 7 章と 8 章の約束を守れているかを確かめる。
2. 22 問それぞれを講座の検索 `search_glossary` で検索し、結果を付ける。
3. Colab にアップロードするファイル `glossary_test.json` に書き出す。

##### 確かめる作業は、これまでの課題でもしていた

- 演習のノートブックのセクション 2 に、質問の重複があればエラーで止める `assert` の 1 行があった。
- 実装のメモの「GPU を使う前に確かめる」でも、必須語句が自分の項目の文にあるか・ほかの項目の文に無いか、を確かめた。
- 発展では照合の数が大きくなる（例えば、必須語句がほかの定義にそろわないかは 16 問 × 64 語 ＝ 1,024 回）。目で確かめると見落とすので、コードにした。
- 実際に、LoRA の必須語句を「行列」だけにしたとき、作った時点では気づかず、コードで初めて「ランク（LoRAのr）」の定義との重なりが分かった。
- このコードは GPU もモデルも使わず、数秒で終わる。Colab で学習したあとに気づくと、学習と評価をやり直すことになる。

##### 確かめるのは 5 つ。確かめないと、エラーが出ないまま正解率が間違う

| 確認 | 確かめないと起きること | 結果への影響 |
|---|---|---|
| 1. 知らない語が、講座の検索で用語集を探しても見つからない | 実は学習した語を「知らない語」として聞いてしまう | 「知らないと言えるか」を測れない |
| 2. 同じ文の質問が、その語の学習データの質問と一字一句同じ | 空白 1 つの違いや、別の語の質問との取り違えで、覚えたかを測れない | 「覚えたか」ではなく「言い換えに強いか」を測ってしまう |
| 3. 言い換えの質問が、学習データのどの質問とも違う | 学習した文そのままを、言い換えとして聞いてしまう | 言い換えの正解率が高く出る |
| 4. 必須語句が、その語の定義にすべてある | 定義をそのまま答えても、語句が無いので不正解になる | 正解率が低く出る |
| 5. 必須語句がすべてそろう定義が、ほかの語に無い | LoRA を聞かれて「ランク（LoRAのr）」の定義を答えても正解になる | 正解率が高く出る。取り違えの失敗が隠れる |

このほかに、テスト問題の書き間違いは、問題を作った時点でエラー（`ValueError`）にして止める。

- 質問の種類（`kind`）が `same`・`paraphrase`・`unknown` のどれでもない。
- 採点の語句に空の文字列 `""` がある。`""` はどんな答えにも含まれるので、何を答えても正解になってしまう。
- 種類と項目の組み合わせが合わない。例えば、知らない語の質問に `must_include` を書いた。

同じ質問が 2 回出てこないかは、22 問なら目で確かめられるので、コードに入れていない。必須語句が質問の文に入っていないか（入っているのは「lecNN-start タグ」の 1 問だけで、2-3 に書いた例外）も同じ。

##### 書き出したファイルには、1 問ごとに検索結果が付く

`glossary_test.json` の 1 問は、次の形になる。`search_result` が講座の検索の結果で、手順 4 の検索ありの方式では、これを質問の前に入れて渡す。

```json
{
  "kind": "same",
  "term_id": "pi",
  "question": "「Pi」とは何ですか？",
  "must_include": ["ターミナル", "コーディングエージェント"],
  "search_result": "用語集に「「Pi」とは何ですか？」は見つかりませんでした。"
}
```

- 見つかった場合の `search_result` は、見つかった語（最大 3 個）の用語名（`term`）・扱う回（`lecture`）・定義（`definition`）・関連語（`related`）を並べた JSON の文字列になる。
- 例の「Pi」は、同じ文の質問なのに見つからなかった。`search_glossary` は、「r」のような短い別名が何にでも一致しないよう、3 文字未満の用語名・id・別名を部分一致に使わない。「Pi」は 2 文字なので、この対象外になった。
  - 直さずに、検索方式の弱点の実例として結果に残す。
- 講座のエージェントでは、モデル自身が検索語（例えば「Pi」）を選んで検索する。今回は質問の文をまるごと渡すので、検索の成績はエージェントで使うときより低めに出る。考察ではこの違いを書いておく。

##### 貼り付け 2：セクション 2 のセル（セル全体を置き換える）

FAQ からデータを作る代わりに、アップロードした 2 つのファイルを読む。ファイルをアップロードしていなければ、その名前を出して止める。読み込んだあとは、件数と、同じ文の質問だけが学習データにあることを確かめ、取り違えたファイルなら止める。

```python
from datetime import datetime
from zoneinfo import ZoneInfo


def log(message: str) -> None:
    """
    進み具合のログを、日本時間の時刻つきで 1 行表示する関数。

    flush=True で、長い処理の途中でもすぐに画面に出す。
    """
    print(f"[{datetime.now(ZoneInfo('Asia/Tokyo')):%H:%M:%S}] {message}", flush=True)


# 手元で作った 2 つのファイルの置き場所（左のファイル一覧から /content にアップロードしておく）
TRAIN_FILE = Path("/content/glossary_sft.jsonl")
TEST_FILE = Path("/content/glossary_test.json")
# missing（見つからないファイルのリスト）: 2 つのうち、/content に無いファイルの名前
missing = [path.name for path in (TRAIN_FILE, TEST_FILE) if not path.exists()]
# アップロードしていないファイルがある場合: 何をすればよいかを書いたエラーで止める
if missing:
    raise FileNotFoundError(f"{', '.join(missing)} がありません。左のファイル一覧から /content にアップロードしてから、このセルを実行し直してください")
# train_rows（学習データ）: 1 行 1 件の {"messages": [user, assistant]} が 130 件
train_rows = [json.loads(line) for line in TRAIN_FILE.read_text(encoding="utf-8").splitlines() if line.strip()]
# test_items（テスト問題）: kind・question・must_include か must_any・search_result を持つ辞書が 22 問
test_items = json.loads(TEST_FILE.read_text(encoding="utf-8"))
# 件数が違う場合は、別のファイルをアップロードしているので止める
assert len(train_rows) == 130, f"学習データが 130 件ではない: {len(train_rows)}"
assert len(test_items) == 22, f"テスト問題が 22 問ではない: {len(test_items)}"

# train_questions（学習データの質問）: 学習データ 130 件の user の文の集合
train_questions = {row["messages"][0]["content"] for row in train_rows}
# 約束 1・2 を Colab でも確かめる（アップロードしたファイルの取り違えに気づくため）
for item in test_items:
    in_train = item["question"] in train_questions
    # 同じ文の質問の場合: 学習データにあるはず
    if item["kind"] == "same":
        assert in_train, f"同じ文の質問が学習データに無い: {item['question']}"
    # 言い換え・知らない語の質問の場合: 学習データに無いはず
    else:
        assert not in_train, f"学習データにある質問がテストに入っている: {item['question']}"

# 読み込みの終わりと件数を表示する
log(f"読み込み完了: 学習データ {len(train_rows)} 件 | テスト問題 {len(test_items)} 問")
# 学習データの 1 件目を表示する
print("学習データの 1 件:", train_rows[0]["messages"])
```

- 進み具合を出す行は、`print()` ではなく、このセルで作る `log()` を使う。中身は `print()` だが、日本時間の時刻を付けること、`flush=True` でためずにすぐ画面に出すこと、表示の形を 1 か所で決められることが違う。時刻があると、表示が止まって見えたときに、最後の行からどれだけたったかで止まっているかを判断できる。結果そのもの（学習データの 1 件目や `result.json` の中身）は `print()` のまま。標準の `logging` モジュールは、ノートブックでは出力先の設定が先に要り、ここで欲しい「時刻付きで、すぐ出る 1 行」には大きすぎるので使わない。

##### 貼り付け 3：セクション 3 の 1 つ目のセル（セル全体を置き換える）

モデルを読み込む部分は演習と同じ。`SYSTEM` を消し、`build_messages` を 2 つの版にした。学習データに system が無いので、評価でも system を入れない。

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

# 使える計算装置を選ぶ（Colab の T4 なら cuda）
DEVICE = "cuda" if torch.cuda.is_available() else ("mps" if torch.backends.mps.is_available() else "cpu")
# 読み込みの開始を表示する（初回はダウンロードがあるので 1〜2 分かかる）
log(f"モデルの読み込みを始める: {CONFIG['base_model']}")
# トークナイザー（文字列とトークンを変換する部品）を読み込む
tok = AutoTokenizer.from_pretrained(CONFIG["base_model"], revision=CONFIG["revision"])
# 埋め草のトークンが無い場合: 文の終わりのトークンで代用する
if tok.pad_token is None: tok.pad_token = tok.eos_token
# 量子化なしで、重みを 32bit のまま読み込み、GPU に載せる
model = AutoModelForCausalLM.from_pretrained(CONFIG["base_model"], revision=CONFIG["revision"], dtype=torch.float32).to(DEVICE)
# 生成を速くするキャッシュを有効にする
model.config.use_cache = True
# 重みが使うメモリを GB で記録する
BASE_MEMORY_GB = round(model.get_memory_footprint() / 1e9, 2)
# 読み込みの終わりと、使う装置・重みのメモリを表示する
log(f"モデルの読み込み完了 | device: {DEVICE} | 重みのメモリ(GB): {BASE_MEMORY_GB}")


def build_messages(item: dict, with_search: bool = False) -> list[dict]:
    """
    モデルに渡すメッセージを作る関数。

    学習データと同じく system は入れず、user に質問だけを入れる。
    答え方の指示は、どちらの版にも足さない（約束 3）。

    Args:
        item: テスト問題 1 問の辞書。
        with_search: True なら、講座の検索結果を質問の前に入れる（検索あり）。

    Returns:
        user の 1 件だけのメッセージのリスト。
    """
    # 検索ありの場合: 検索結果と質問を入れる
    if with_search:
        content = f"用語集の検索結果:\n{item['search_result']}\n\n質問: {item['question']}"
    # 学習前・学習後の場合: 質問だけを入れる
    else:
        content = item["question"]
    return [{"role": "user", "content": content}]


def generate(model, item: dict, with_search: bool = False) -> str:
    """
    1 問に答えさせ、答えの文字列を返す関数。

    Args:
        model: 答えさせるモデル（学習前の model か、学習後の tuned）。
        item: テスト問題 1 問の辞書。
        with_search: True なら、検索ありの版で質問する。

    Returns:
        モデルが生成した答えの文字列（前後の空白は除く）。
    """
    # メッセージをモデル用の文字列にする。enable_thinking=False で、思考ブロックを空にして答えだけを生成させる
    prompt = tok.apply_chat_template(build_messages(item, with_search), tokenize=False, add_generation_prompt=True, enable_thinking=False)
    # 文字列をトークンに変え、モデルと同じ装置に載せる
    inputs = tok(prompt, return_tensors="pt").to(model.device)
    # 学習はしないので、勾配を計算せずに生成する
    with torch.no_grad():
        out = model.generate(**inputs, max_new_tokens=CONFIG["max_new_tokens"], pad_token_id=tok.pad_token_id, **CONFIG["gen"])
    # 入力の部分を除き、生成した部分だけを文字列に戻す
    return tok.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True).strip()
```

##### 貼り付け 4：セクション 3 の 2 つ目のセル（セル全体を置き換える）

JSON の形式の採点を、`must_include`・`must_any` の採点に変えた。学習前と検索ありの 2 つを、ここで続けて評価する。検索ありを学習の前に済ませるのは、学習後は `model` にも adapter が入るため。

```python
import pandas as pd
# 表の中の答えの原文を、省略せずに表示する
pd.set_option("display.max_colwidth", None)

# 別名で聞く言い換えの質問の語。残りの言い換え 4 問は、用語名も別名も出さずに聞く質問
ALIAS_TERM_IDS = {"homework-levels", "default-model", "lora", "temperature"}
# 結果の表で使う、質問の種類の呼び名（言い換えは 2 つに分ける）
GROUP_NAMES = {"same": "同じ文", "alias": "言い換え（別名）", "no_name": "言い換え（用語名なし）", "unknown": "知らない語"}


def group_of(item: dict) -> str:
    """
    テスト問題 1 問を、結果の表の 4 つの種類に分ける関数。

    Args:
        item: テスト問題 1 問の辞書。

    Returns:
        GROUP_NAMES のキー（same・alias・no_name・unknown のどれか）。
    """
    # 言い換えの質問の場合: 別名で聞いたか、用語名も別名も出さずに聞いたかで分ける
    if item["kind"] == "paraphrase":
        return "alias" if item["term_id"] in ALIAS_TERM_IDS else "no_name"
    # 同じ文・知らない語の場合: 種類のまま
    return item["kind"]


def score(item: dict, raw: str) -> bool:
    """
    答えが正解かを判定する関数。

    Args:
        item: テスト問題 1 問の辞書。
        raw: モデルの答えの文字列。

    Returns:
        正解なら True。
    """
    # 同じ文・言い換えの場合: 必須語句をすべて含めば正解
    if "must_include" in item:
        return all(word in raw for word in item["must_include"])
    # 知らない語の場合: 「知らない」を表す語句をどれか 1 つ含めば正解
    return any(word in raw for word in item["must_any"])


def mark(ok: bool) -> str:
    """
    正解なら ○、不正解なら × を返す関数。
    """
    return "○" if ok else "×"


def evaluate(model, label: str, with_search: bool = False) -> tuple[dict, list[dict]]:
    """
    22 問に答えさせて採点し、種類ごとの正解の数と 1 問ごとの結果を返す関数。

    答えの原文は eval_<label>.json に保存する。

    Args:
        model: 答えさせるモデル。
        label: 方式の名前（before・search・after）。保存するファイル名にも使う。
        with_search: True なら、検索ありの版で質問する。

    Returns:
        種類ごとの正解の数をまとめた辞書と、1 問ごとの結果の辞書のリスト。
    """
    # rows（1 問ごとの結果）: 種類・質問・答えの原文・正解か、を持つ辞書のリスト
    rows = []
    t0 = time.time()
    # 評価の開始を表示する
    log(f"{label} の評価を始める（{len(test_items)} 問、1 問ずつ進み具合を表示する）")
    for number, item in enumerate(test_items, start=1):
        raw = generate(model, item, with_search)
        rows.append({"group": group_of(item), "term_id": item["term_id"], "question": item["question"], "raw": raw, "ok": score(item, raw)})
        # 進み具合を 1 問ごとに表示する（止まっていないかを確かめるため）
        log(f"{label}: {number}/{len(test_items)} 問 | {mark(rows[-1]['ok'])} | 経過 {time.time() - t0:.0f} 秒 | {item['question']}")
    # summary（方式ごとのまとめ）: 方式の名前、問題の数、種類ごとの正解の数、かかった秒数
    summary = {"label": label, "n": len(rows)}
    # 種類ごとに、正解した数と問題の数を「3/8」の形で記録する
    for group, name in GROUP_NAMES.items():
        group_rows = [row for row in rows if row["group"] == group]
        summary[name] = f"{sum(row['ok'] for row in group_rows)}/{len(group_rows)}"
    summary["合計"] = f"{sum(row['ok'] for row in rows)}/{len(rows)}"
    summary["seconds"] = round(time.time() - t0, 1)
    (WORK / f"eval_{label}.json").write_text(json.dumps({"summary": summary, "rows": rows}, ensure_ascii=False, indent=2), encoding="utf-8")
    # 評価の終わりと、種類ごとの正解の数を表示する
    log(f"{label} の評価完了: {json.dumps(summary, ensure_ascii=False)}")
    return summary, rows


# 学習前（質問だけ）と、検索あり（学習前のモデルに検索結果を渡す）を、学習の前に済ませる
before_summary, before_rows = evaluate(model, "before")
search_summary, search_rows = evaluate(model, "search", with_search=True)
# 1 問ごとに、学習前と検索ありの答えと ○× を並べて表示する
display(pd.DataFrame([{"種類": GROUP_NAMES[b["group"]], "質問": b["question"],
                       "学習前の答え": b["raw"], "学習前": mark(b["ok"]),
                       "検索ありの答え": s["raw"], "検索あり": mark(s["ok"])} for b, s in zip(before_rows, search_rows)]))
```

- `ALIAS_TERM_IDS` は、言い換えの質問を「別名で聞いた 4 問」と「用語名も別名も出さずに聞いた 4 問」に分けるための、語の id の集合。手順 5 の表で、この 2 つを分けて書くために使う。
- `group_of` は「〜の group（まとまり）」という英語の読み方に合わせた名前。`group_of(item)` は「item の group」と読め、1 問が入る表の種類を返すという動作と一致する。値を調べて返すだけなので動詞で始めず、テスト問題がもともと持つ 3 種類の `kind` と区別するため、4 つの分け方には `group` という別の言葉を使った。

### ステップ 2：テスト問題 1 問を dataclass で表す

```python
# frozen=True で、作ったあとに値を書き換えられないようにする
@dataclass(frozen=True)
class EvalItem:
    # 質問の種類（same・paraphrase・unknown）
    kind: Kind
    # モデルに渡す質問の文
    question: str
    # 答えになる用語集の語の id。知らない語では None
    term_id: str | None = None
    # すべて含めば正解にする語句（同じ文・言い換えで使う）
    must_include: tuple[str, ...] = ()
    # どれか 1 つを含めば正解にする語句（知らない語で使う）
    must_any: tuple[str, ...] = ()
```

- `@dataclass` は、項目を並べて書くだけで、値を入れて作る処理（`__init__`）を自動で用意する、Python 標準の仕組み。
- 1 問を辞書（`{"kind": "same", ...}`）で書くと、キーの書き間違いや、項目の組み合わせの間違いがエラーにならない。クラスにすると、作った時点で確かめられる。
- pydantic（パイダンティック。外から来るデータの型を検査するライブラリ）は使わない。テスト問題はこのファイルの中に自分で書く値なので、標準の dataclass で足りる。
- 22 問は、`EvalItem("same", "「LoRA」とは何ですか？", "lora", must_include=("行列", "固定"))` のように書く。引数の順は（種類, 質問の文, 用語集の id）。

作った直後に呼ばれる `__post_init__` が、書き間違いを止める。

```python
# 種類が 3 つのどれでもない場合（Literal は実行時に確かめないので、ここで確かめる）
if self.kind not in get_args(Kind):
    raise ValueError(f"質問の種類が正しくない: {self.kind}")
# 空の語句がある場合（"" はどんな答えにも含まれるので、何を答えても正解になってしまう）
if any(not word.strip() for word in self.must_include + self.must_any):
    raise ValueError(f"採点の語句に空の文字列がある: {self.question}")
```

- `Kind = Literal["same", "paraphrase", "unknown"]` は、3 つの文字列だけを表す型。ただし、型は VS Code などのエディタが見る目印で、実行時には確かめない。`"smae"` と書いても動いてしまう。
- `get_args(Kind)` は、`Literal` から `("same", "paraphrase", "unknown")` を取り出す関数。これと比べて、実行時に確かめる。
- `word.strip()` は、前後の空白を取り除いた文字列を返す。空白だけの語句も、空として扱う。

### ステップ 3：学習データの質問を作り直す

```python
# by_id（id から語を引く辞書）: 例えば by_id["pi"]["definition"] で Pi の定義が取れる
by_id = {term["id"]: term for term in terms}
# train_questions（学習データの質問）: 65 語 × ひな形 2 つで作り直した 130 個の集合
train_questions = {template.format(term=term["term"]) for term in terms for template in TEMPLATES}
```

- `by_id` は、テスト問題の `term_id` から、その語の用語名と定義を取り出すために作る。リストのままだと、毎回 65 個を先頭から探すことになる。
- `{… for term in terms for template in TEMPLATES}` は、2 重のループで集合を作る書き方（集合内包表記）。語 1 つにつき、ひな形 2 つを当てはめる。例えば語が「宿題の3レベル」なら、`"「宿題の3レベル」とは何ですか？"` と `"宿題の3レベルについて簡単に説明してください。"` の 2 つができる。
- `glossary_sft.jsonl` を読まずに作り直すのは、ファイルの置き場所に関係なく確認できるようにするため。ひな形がスクリプトと同じなので、同じ 130 個になる。
- 集合（`set`）にするのは、「この質問は含まれるか」を速く調べられるため。

### ステップ 4：確認 1〜5 を行う

確認 1 は、知らない語を、質問の「」の中から取り出して検索する。

```python
# match（「」の中を探した結果）: group(1) で「」の中の語が取れる。「」が無ければ None
match = re.search(r"「(.+?)」", item.question)
# 「」が無い場合
if match is None:
    problems.append(f"知らない語の質問に「」が無い: {item.question}")
# 「」の中の語が、用語集で見つかった場合
elif not search_glossary(match.group(1)).startswith(NOT_FOUND_PREFIX):
    problems.append(f"知らない語が用語集で見つかった: {match.group(1)}")
```

- `re.search(パターン, 文字列)` は、文字列の中からパターン（正規表現）に合う部分を探す。
  - `「(.+?)」` は、「 と 」に挟まれた 1 文字以上の部分を表す。`( )` で囲んだ部分が、`group(1)` で取り出せる。
  - `?` を付けると、なるべく短く一致させる。
- `NOT_FOUND_PREFIX` は `"用語集に"`。見つかった場合、`search_glossary` は `[` で始まる JSON の文字列を返すので、`startswith` で見分けられる。
- 検索は、用語名・id・別名・定義のどこかに一致すれば見つける。そのため、「定義の中に出てくる語」まで含めて、用語集に無いことを確かめられる。
- 知らない語の質問は、このあと `continue` で次の問題へ進む。定義が無いので、確認 2〜5 はしない。

確認 2 は、同じ文の質問が、その語の学習データの質問と一字一句同じかを確かめる。

```python
# 確認 2: 同じ文の質問が、その語の学習データの質問と違う場合
expected_question = TEMPLATES[0].format(term=by_id[item.term_id]["term"])
if item.kind == "same" and item.question != expected_question:
    problems.append(f"同じ文の質問が {item.term_id} の学習データの質問と違う: {item.question}")
```

- `expected_question` は、`term_id` の語の用語名を、1 つ目のひな形に入れた文。`term_id` が `"lora"` なら `"「LoRA」とは何ですか？"` になる。
- 130 個のどれかと同じか、ではなく、その語の質問と同じかを見る。`term_id` を `"lora"` にしたまま Pi の質問を書いても、学習データにはある文なので、前者では見逃してしまう。

確認 5 は、必須語句がすべてそろう定義が、ほかの語に無いかを確かめる。

```python
# 確認 5: ほかの語の定義に、必須語句がすべてそろう場合
for term in terms:
    if term["id"] != item.term_id and all(word in term["definition"] for word in item.must_include):
        problems.append(f"{item.term_id} の必須語句が {term['id']} の定義にもそろう")
```

- `all(…)` は、中の条件がすべて真なら真を返す関数。`word in term["definition"] for word in item.must_include` は、必須語句を 1 つずつ取り出して「定義に含まれるか」を調べる。
- LoRA の必須語句が「行列」だけだったときの値は、次のとおり。
  - `item.must_include` は `("行列",)` だった。
  - `term` が「ランク（LoRAのr）」の語のとき、定義は `"LoRAで使う低ランク行列の大きさを決める…"`。
  - 「行列」が含まれるので `all(…)` が真になり、問題として記録された。
- 「行列」「固定」に直すと、「ランク（LoRAのr）」の定義に「固定」が無いので、`all(…)` は偽になる。

確認 3 は `item.question in train_questions`、確認 4 は `all(word in own_definition for word in item.must_include)` で、どちらも上と同じ書き方。

### ステップ 5：問題が無いときだけ、検索結果を付けて書き出す

```python
# 問題がある場合: 表示して、ファイルは書き出さずに終える
if problems:
    print("\n".join(problems), file=sys.stderr)
    return 1

# 1 問ずつ、質問の文をそのまま講座の検索に渡し、結果を付ける
records = [item.to_json_dict(search_glossary(item.question)) for item in TEST_ITEMS]
```

- 問題があるときに書き出さないのは、間違ったテスト問題のファイルを Colab に持っていかないようにするため。
- `to_json_dict()` は、1 問を辞書にするメソッド。採点に使うキーは、種類に合う方（`must_include` か `must_any`）だけを入れ、最後に `search_result` を足す。
- `json.dumps(…, ensure_ascii=False)` は、日本語を `実` のような記号に変えずに、そのまま書き出すための指定。

### ステップ 6：終了コードを OS に渡す

```python
# 直接実行した場合: main() の戻り値（0 か 1）を終了コードにして終える
if __name__ == "__main__":
    sys.exit(main())
```

- `sys.exit()` は、プログラムを終わらせて、終了コードを OS に渡す関数。
- 無くても画面に出る文は同じだが、問題があっても終了コードが 0（成功）になる。実際に、問題がある状態で `sys.exit` を外すと終了コードが 0 になり、`&&`（前のコマンドが成功したときだけ後ろを実行する記号）の後ろのコマンドが実行された。
