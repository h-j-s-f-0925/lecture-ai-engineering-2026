# 第2回 宿題 実装 メモ：講座リポジトリのコマンド FAQ

## 題材

- 講座リポジトリのコマンド FAQ（5 項目）にする。
- FAQ の文は `lectures/01/problem.md` と `lectures/03/problem.md` に書かれている事実から作る。
- 講座リポジトリにしかない名前（`app.ask`、`AIE_MODEL`、`lecNN-start` など）が中心なので、モデルは事前学習で知らないと考えられる。
  - 根拠ありの質問に正解したら、FAQ を読んで答えたと言える。
  - 根拠なしの質問に断定したら、FAQ の別の項目を流用したと分かる。

| キー | FAQ の出典 | 必須語句 |
|---|---|---|
| `ask` | `lectures/01/problem.md:47` | `app.ask` |
| `model` | `lectures/01/problem.md:84` | `AIE_MODEL` |
| `tools` | `lectures/03/problem.md:83` | `--list-tools` |
| `trace` | `lectures/03/problem.md:52` | `--trace` |
| `start_tag` | `lectures/03/problem.md:34-38` | `lecNN-start` |

## 題材の選び方

### 一番のポイント：モデルが知らない題材にする

- この宿題で確かめたいのは、「FAQ だけを根拠に答え、FAQ に無いことは確認を求められるか」。
- モデルが知っている題材だと、次の 2 つが区別できない。
  - 根拠ありの質問に正解しても、FAQ を読んだのか、もともとの知識で答えたのか分からない。
  - 根拠なしの質問で断定しても、FAQ の別の項目を流用したのか、もともとの知識で答えたのか分からない。
- 元の教材が架空の講座 FAQ を使っているのも、このためだと考えられる（ノートブックに理由は書かれていないので推測）。

### モデルが知らない題材の種類

モデルは、インターネットに公開されていて何度も書かれている事実をよく知っている。「公開されていない」「書かれた回数が少ない」「学習した後にできた」のどれかに当てはまる事実が候補になる。

| 種類 | 例 | 使いやすさ | 注意点 |
|---|---|---|---|
| ① 架空の設定（自分で作る） | 架空の講座、店、ゲームのルール、社内規程（元の教材の方式） | ◎ | 作り話なので、正しいかを確かめる手間がない |
| ② 特定の環境にしかない事実 | 講座リポジトリのコマンド（今回の題材） | ◎ | 実際に書かれている文を出典にできる |
| ③ 細かすぎて一般には書かれない事実 | 特定の資料の何ページ目に何があるか、ある設定ファイルの値 | ○ | 一般的な用語と混ざると、知っている部分が出てくる |
| ④ 意味を入れ替えた設定 | 「この講座では LoRA の r を 7 に固定する」のような、知っている用語に普通とは違う決まりを付けたもの | △ | FAQ ともともとの知識がぶつかるので、難しい実験になる |
| ⑤ モデルが学習した後の出来事 | 最近の出来事や新しい製品 | △ | モデルがいつまでのデータで学習したかが分からず、確かめにくい |
| ⑥ 公開されていない内部情報 | 実際の会社や組織の手順 | × | 機密や個人情報になるので使わない。使うなら①の架空の形に作り直す |

題材に向かないもの：一般常識、有名な技術用語（LoRA、SFT など）、百科事典に載っている事実、料金のように頻繁に変わる実在の情報、自分の個人情報。

### 「知らない」以外に必要な条件

1. 5 項目を、1 項目 1 つの事実として書ける。
2. 項目ごとに、その項目にしか出てこない語（必須語句にする語）がある。
3. 1 つの文が 50 文字くらいに収まる。
4. 近い外れ（同じ話題だが答えが書いていない質問）を作りやすい。
5. 正しいかを自分で確かめられる（出典がある、または自分で決めた架空の設定）。

### 本当に知らないかを確かめる方法

- 検索してみる。答えがインターネットのあちこちに書かれていたら、モデルが学習している可能性が高い。
- ノートブックのセクション 3 の学習前の出力を見る。FAQ に無い事実がそれらしく出てきたら、もともとの知識が混ざっている。
- FAQ を渡さずに聞く（一番確実）。FAQ を空にして根拠ありの質問をし、正しく答えられたらその題材は知られている。ノートブックにこの確認用のセルは無いので、自分で足す必要がある。

### 今回の題材選びの流れ

1. 最初は第 2 回の講義の要点（LoRA、SFT など）を FAQ にしようとした（末尾の「前の下書き」）。
2. 有名な技術用語はモデルが知っているので、FAQ を読んで答えたのか区別できないと分かった。
3. 種類②の「特定の環境にしかない事実」として、講座リポジトリのコマンドを選んだ。
4. 候補には、開発環境の困りごと FAQ（Codespaces の Secrets、Sync fork の Discard commits など）もあった。ただ、`Secrets` や `Discard commits` は GitHub の一般的な機能で、モデルが知っている可能性がある。そのため、`app.ask` や `AIE_MODEL` のような講座にしかない名前が中心のコマンド FAQ にした。

## 根拠なしの質問の用意の仕方

- 近い外れ（FAQ と同じ話題だが、答えが FAQ に書いていない質問）を中心にし、遠い外れ（話題ごと FAQ に無い質問）を少しまぜた。12 問のうち近い外れが 9 問、遠い外れが 3 問。
- 一部の質問には FAQ の語（`AIE_MODEL`、`--trace` など）をわざと含めた。質問の語につられて FAQ の文を写し、断定するかを見るため。元の教材で残った失敗「オフィスアワーは事前予約が必要ですか」と同じ型にあたる。
- test に入る根拠なしの 6 問の内訳は、近い外れ 5 問、遠い外れ 1 問。

### 整理の軸

今の「FAQ との距離」のほかにも、次の軸で整理できる。`answer.md` では、①に④と⑧を足すのがよい。この 2 つは、ファインチューニングと RAG の比較、学習の効果の考察に直接つながる。

| 軸 | 分け方 | この軸で見えること |
|---|---|---|
| ① FAQ との距離 | 近い外れ／遠い外れ | 話題が近いほど断定しやすいか |
| ② FAQ の語を含むか | 含む／含まない | 質問の語につられて FAQ の文を写すか |
| ③ 欠けている情報の種類 | 値・数量／できるかどうか／条件・例外／手順／時期 | どの種類の質問で断定しやすいか |
| ④ 答えが講座の資料にあるか | FAQ には無いが資料やコードにある／外部にある／どこにも無い | 検索（RAG）なら答えられた質問はどれか |
| ⑤ モデルが一般知識で答えられそうか | 講座固有／一般の事実（料金など） | 事前学習の知識で断定するか |
| ⑥ 質問の形 | はい・いいえで答える形／値を聞く形／方法を聞く形 | 「はい」と答えやすい形で断定が増えるか |
| ⑦ 間違えたときの影響 | 作業を壊す／時間やお金を損する／困らない | 確認を求めることが特に大事な質問はどれか |
| ⑧ 置き場所 | train／valid／test を FAQ の項目ごとに見る | 学習で見た項目と見ていない項目で差が出るか |

### 12 問への当てはめ

④の「資料にある」「コードにある」は、リポジトリ内で答えを確かめた質問だけに付けた。

| 質問 | ① 距離 | ② FAQ の語 | ③ 欠けている情報 | ④ 答えのありか | ⑥ 形 | ⑧ 置き場所 |
|---|---|---|---|---|---|---|
| app.ask で会話の履歴は残りますか | 近（ask） | 含む | できるかどうか | 未確認 | はい・いいえ | train |
| Gemini API の料金はいくらですか | 遠 | 含まない | 値・数量 | 外部（公式サイト） | 値 | train |
| AIE_MODEL に指定できるモデルの一覧は？ | 近（model） | 含む | 値・数量 | 外部 | 値 | valid |
| --trace の出力をファイルに保存できますか | 近（trace） | 含む | できるかどうか | 未確認 | はい・いいえ | test |
| ツールを自分で追加するにはどのファイルを直しますか | 近（tools） | 含まない | 手順 | 資料（`lectures/03/problem.md:68` の `app/tools.py`） | 方法 | train |
| Codespaces の無料枠は月に何時間ですか | 遠 | 含まない | 値・数量 | 外部 | 値 | train |
| 開始タグを消してしまったらどうなりますか | 近（start_tag） | 含まない | 条件・例外 | 未確認 | 方法 | valid |
| AIE_MODEL を設定しないとどのモデルが使われますか | 近（model） | 含む | 条件・例外 | コード（`app/config.py:12` の既定モデル） | 値 | test |
| app.ask の回答を英語にできますか | 近（ask） | 含む | できるかどうか | 未確認 | はい・いいえ | test |
| --list-tools の表示に引数の説明は出ますか | 近（tools） | 含む | できるかどうか | 未確認 | はい・いいえ | test |
| lecNN-start タグはいつ公開されますか | 近（start_tag） | 含む | 時期 | どこにも無い | 値 | test |
| 講座の修了証はもらえますか | 遠 | 含まない | できるかどうか | 資料（講義スライドに「修了証（PDF）を授与」） | はい・いいえ | test |

- ⑤：Gemini API の料金と Codespaces の無料枠が一般の事実で、それ以外は講座固有。
- ⑦：「開始タグを消してしまったら」が作業を壊す側、料金と無料枠がお金を損する側で、それ以外は大きくは困らない。

### 整理して見えた、今のデータの特徴

- 近い外れを train で見ているのは、5 項目中 2 項目だけ。
  - `ask` と `tools`：近い外れが train にも test にもある。
  - `model` と `start_tag`：valid と test にしか無い。
  - `trace`：test にしか無い。
  - 学習で近い外れを見た項目と見ていない項目で、断定の起きやすさが違うかを比べられる。
- FAQ には無いが、資料やコードには答えがある質問が 3 問ある（どのファイルを直すか、既定のモデル、修了証）。FAQ だけを根拠にすれば確認を求めるのが正解だが、第 5 回の RAG なら答えられた可能性がある。「ファインチューニングでは答えを持たせず、検索で補う」という考察の具体例になる。
- はい・いいえで答える形が 5 問ある。ここで `needs_review: false` と「はい」が出たら、⑥の型の断定として分類できる。

## データ作りで気づいたこと

### 元のデータの作り方

- `FAQ`・`GROUNDED`・`UNGROUNDED` に元データは無い。ノートブックのセクション 2 のセルに、教材の作者が手で書いた架空のデータ。
- 人が手で書くのは、`FAQ`（回答文 5 つ）、`GROUNDED`（言い換えの質問 4 つと必須語句）、`UNGROUNDED`（FAQ に無い質問 8 つ）、`TEST_EXTRA_...`（test 専用の質問）の 4 つだけ。train・valid・test への振り分けと正解（`gold`）の作成は、下のコードが自動で行う。
- 正解の answer として新しい文は書いていない。根拠ありの質問は `FAQ` の文をそのまま使い、根拠なしの質問は固定文「この FAQ には記載がありません。運営に確認が必要です。」を使う。そのため、必須語句は `FAQ` の文から抜き出した部分文字列になる。

### 並び順に意味がある

- `GROUNDED` の 4 つの質問は、1・2 番目が train、3 番目が valid、4 番目が test に入る。
- `UNGROUNDED` の 8 問は、並び順の番号を 4 で割った余り（`i % 4`）で振り分けられる。余りが 0 と 1 なら train、2 なら valid、3 なら test。test に入るのは 4 番目と 8 番目なので、確かめたい質問はそこに置く。
- 件数を元と同じにすれば、train 14 / valid 7 / test 21 になり、元の結果とそのまま比べられる。

### つまずいた点と直し方

| つまずいた点 | 何が起きるか | 直し方 |
|---|---|---|
| 辞書のキーをすべて `""` にした | Python の辞書は同じキーを何度書いても最後の 1 つしか残らない。`FAQ` が 1 項目になる | 項目ごとに別の名前のキーを付ける（`"ask"` など） |
| 1 項目の文が長い（最長 141 文字） | `CONFIG` の `"max_new_tokens": 96` を超え、出力の JSON が途中で切れるおそれがある | 1 項目 1 つの事実にし、50 文字くらいにする（元の FAQ は 19〜42 文字） |
| 文の中に主語の用語が無い（LoRA の文に「LoRA」が無い） | 質問とどの項目が対応するか、モデルも採点も結び付けにくい | 文の主語に用語を入れる |
| 項目同士の内容が重なる（「講義の狙い」と「向く場面」） | どちらの項目が正解か決められない | 1 項目 1 つの事実にし、重なる項目を入れ替える |
| 必須語句がほかの項目の文に部分一致した（開発環境 FAQ の案で、`commit` が `Discard commits` の中に含まれた） | 別の項目の文で答えても正解と判定される | その項目にしか無い語を必須語句に足す（`["前の回のブランチ", "commit"]`）。採点は必須語句がすべて含まれるかで判定するので、取り違えは不正解になる |

### GPU を使う前に確かめる

セクション 2 は GPU もモデルも使わないので、ローカルで先に確かめられる。確かめるのは次の 4 点。

1. 件数と重複：`train=14 valid=7 test=21 gold=21` になり、ノートブックの `assert` が通るか。
2. 必須語句が自分の項目の文にあるか：無いと、FAQ の文を正しく写しても不正解になる。
3. 必須語句がほかの項目の文に無いか：あると、別の項目の文で答えても正解になる。
4. 知識質問（セクション 6）：FAQ に無い 3 問が学習・評価データに入っておらず、対照の 1 問が test にあるか。

### 質問の書き方

- 根拠ありの質問は、場所・方法・症状・短い聞き方のように角度を変えると、言い換えが自然に出てくる。
- 根拠ありの質問の文には必須語句を入れない。質問から写しただけで正解になるのを避けるため。

## 貼り付け 1：セクション 2 のセル（セル全体を置き換える）

```python
FAQ = {
    "ask": "質問を 1 回送るには uv run python -m app.ask を使います。",
    "model": "使うモデルは AIE_MODEL という環境変数で切り替えます。",
    "tools": "エージェントのツール一覧は app.agent に --list-tools を付けると表示されます。",

    "tools": (["エージェントが使えるツールを一覧で見るには？", "ツールの一覧を表示する方法を教えてください", "モデルに見えているツールを確認したいです", "ツール一覧を出すオプションは？"], ["--list-tools"]),
    "trace": (["ツールがどう呼ばれたか確認するには？", "エージェントの途中の動きを見る方法を教えてください", "どのツールがどの引数で呼ばれたか知りたいです", "ツール呼び出しを表示するオプションは？"], ["--trace"]),
    "start_tag": (["各回の開始時点のコードはどう取り出しますか", "講座の最初の状態からブランチを作るには？", "その回の初期コードから始める方法を教えてください", "開始時点のコードに付いているタグは？"], ["lecNN-start"]),
}
# 根拠なし: FAQ に無いので needs_review=true が正解
UNGROUNDED = [
    "app.ask で会話の履歴は残りますか", "Gemini API の料金はいくらですか", "AIE_MODEL に指定できるモデルの一覧は？",

    "開始タグを消してしまったらどうなりますか", "AIE_MODEL を設定しないとどのモデルが使われますか",
]

# test 専用の追加質問（train / valid には入れない）
TEST_EXTRA_GROUNDED = {
    "ask": ["質問を 1 つ投げて答えを見るには何を実行しますか", "単発の質問に使う uv run のコマンドを教えてください"],
    "model": ["Gemini のモデル名を変えて実行するには何を使いますか", "実行するモデルはどの環境変数で決まりますか"],
    "tools": ["app.agent で利用できるツールを表示するには？", "エージェントのツール名をまとめて確認する方法は？"],
    "trace": ["エージェントのツール呼び出しの様子を見るオプションを教えてください", "app.agent の実行中にどのツールが使われたか確かめるには？"],
    "start_tag": ["作業ブランチはどのタグから作りますか", "各回のスタート地点のコードを使うにはどうしますか"],
}
TEST_EXTRA_UNGROUNDED = [
    "app.ask の回答を英語にできますか", "--list-tools の表示に引数の説明は出ますか",
    "lecNN-start タグはいつ公開されますか", "講座の修了証はもらえますか",
]
UNGROUNDED_ANSWER = "この FAQ には記載がありません。運営に確認が必要です。"

def make_example(question: str, answer: str, needs_review: bool) -> dict:
    target = json.dumps({"answer": answer, "needs_review": needs_review}, ensure_ascii=False)
    return {"question": question, "faq": FAQ_TEXT, "target": target, "needs_review": needs_review}

def split_templates(templates):
    # テンプレートの先頭 2 つを train、3 つ目を valid、4 つ目を test に固定（言い換えを跨がせない）
    return templates[:2], templates[2:3], templates[3:4]

train, valid, test, gold = [], [], [], {}
for key, (templates, must_include) in GROUNDED.items():
    tr, va, te = split_templates(templates)
    for q in tr: train.append(make_example(q, FAQ[key], False))
    for q in va: valid.append(make_example(q, FAQ[key], False))
    for q in te + TEST_EXTRA_GROUNDED[key]:
        test.append(make_example(q, FAQ[key], False)); gold[q] = {"needs_review": False, "must_include": must_include}
for i, q in enumerate(UNGROUNDED):
    ex = make_example(q, UNGROUNDED_ANSWER, True)
    bucket = [train, train, valid, test][i % 4]   # 根拠なしの質問は 4 問ごとに train 2 / valid 1 / test 1 に振る
    bucket.append(ex)
    if bucket is test: gold[q] = {"needs_review": True, "must_include": ["確認"]}
for q in TEST_EXTRA_UNGROUNDED:
    test.append(make_example(q, UNGROUNDED_ANSWER, True)); gold[q] = {"needs_review": True, "must_include": ["確認"]}

# train は 14 件（根拠あり 10、根拠なし 4）。同じ例を何回学習するかは、データを複製せず、セクション 4 の num_train_epochs で決める
all_questions = [r["question"] for r in train + valid + test]
assert len(set(all_questions)) == len(all_questions), "質問が train / valid / test のどこかで重複しています。テンプレートを見直してください"
print(f"train={len(train)} valid={len(valid)} test={len(test)} gold={len(gold)}")
print("学習例の 1 件 | 質問:", train[0]["question"], "| 望ましい出力:", train[0]["target"])
_ = (WORK / "train.jsonl").write_text("\n".join(json.dumps(r, ensure_ascii=False) for r in train), encoding="utf-8")
_ = (WORK / "test.jsonl").write_text("\n".join(json.dumps(r, ensure_ascii=False) for r in test), encoding="utf-8")
_ = (WORK / "gold.json").write_text(json.dumps(gold, ensure_ascii=False, indent=2), encoding="utf-8")
```

実行すると `train=14 valid=7 test=21 gold=21` と表示されれば正しい。
