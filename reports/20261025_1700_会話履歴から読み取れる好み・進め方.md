# 会話から読み取れる好み・進め方

この文書は、この会話での依頼やフィードバックから読み取れる傾向をまとめたものです。明示された指示ではなく、会話に基づく暫定的な理解として扱ってください。

## 好み

- 実行結果は、後から確認・比較できるようファイルに残したい。
- 出力は一目で概要が分かることを重視する。詳細はサマリーの後に置き、必要なときだけ読める形がよい。
- モデルの回答そのものと、自分の要約・考察を区別したい。
- 実験条件や実行単位を記録し、結果の根拠をたどれるようにしたい。
- 人が読む Markdown では、見出し、表、改行、折りたたみなどで読みやすく整理したい。
- スクリプトは動くだけでなく、各行の意味も理解しながら使いたい。
- 特にシェルの記法（例：`$#`、`2>&1`）やコマンドの役割を、具体的で平易な日本語コメントで知りたい。
- 命名は用途が分かるものを好む。Markdown レポートの保存先なら `logs/` より `reports/` のように内容を正確に表す名前がよい。
- 固定の説明と実行ごとに変わる内容は分けて管理したい。レポートの固定部分をテンプレートにし、動的な結果はスクリプトで生成する構成に関心がある。

## 書きぶり・やりとり

- 日本語で、短く具体的に依頼する傾向がある。
- 「どうするのがよいか」を相談した後、方針が固まったら実装を依頼する。
- 抽象的な説明だけでなく、実際の出力例やファイル構成、実行方法を見ながら進めたい。
- 一度に大きく作り替えるより、出力を確認して小さく改善していく進め方が合っている。
- 説明は初心者にも追えるように、専門用語やシェル構文の意味を添えることを重視する。

## 作業時に配慮するとよさそうなこと

- まず完成形の Markdown 出力例を示し、見た目と情報の並びを確認できるようにする。
- 回答全文は加工せず残し、条件・メタデータ・要約と分ける。
- サマリー表を冒頭に置き、詳細な回答は折りたたむなどして一覧性を保つ。
- スクリプトを変更したときは、構文チェックに加え、可能なら API を使わないモックで生成結果を確認する。
- 新しい用語や処理を導入する場合は、コードコメントや README に目的と使い方を平易に説明する。
