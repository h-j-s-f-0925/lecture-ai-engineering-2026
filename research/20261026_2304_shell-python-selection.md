# シェルスクリプトと Python の役割分担、および今回の変更判断

## 結論

シェルか Python かに、どの案件にも当てはまる絶対的な正解はありません。一言でいうと、**シェルはコマンドをつなぐ道具、Python は構造化データやアプリケーションの処理を書く言語**です。シェルで扱う処理が短いコマンド連携を超えて、複雑な分岐・配列・集計・レポート加工に広がるなら Python を検討する根拠があります。

今回 Python runner に移した理由は、API呼び出し計測、モデル・質問・試行の組み合わせ、利用量の保持、統計、Markdown生成を、構造化した Python の値で一貫して扱い、既存CLIの人間向け出力を `sed` で解析しないためでした。これは合理性のある技術案です。また、移行前の `run.sh` は233行あり、Google Shell Style Guideの「100行を超えるスクリプトは構造化言語への書き換えを検討する」という勧告にも該当します。

しかし、**その勧告はGoogleのスタイルガイドであり、普遍的な規則ではありません**。この宿題でシェルを使うこと自体が学習目的である可能性や、ユーザーが `run.sh` の実装主体も維持したい意図を優先するかは、コードの行数だけからは分かりません。実際には `run.sh` を実質的な実験処理から9行の起動ラッパーにし、471行の `app/benchmark.py` に責務を移しました。コマンドの入口は保たれたものの、内部構成は大きく変わっています。

したがって、**Python化を技術的な候補として提案することは妥当でしたが、実装を始める前にユーザーの選択を確認せず採用したのは不適切でした**。ユーザーはシェルの学習も希望しているため、基礎用 `run.sh` は従来どおりのBash実装として残し、発展用Python runnerは `run-advanced.sh` という別入口に分ける方針が適切です。こうすれば基礎ではシェルの実装を学びつつ、発展課題ではAPI応答や複数条件の集計を構造化データで扱えます。発展課題自体もシェルで実装したい場合は、シェル主導ハイブリッドを別案として選べます。

## 調査対象・前提

- 対象リポジトリの構成：Python 3.12 と `uv`、Gemini SDKを使う第1回実験。依存関係は既存設定を確認し、今回の言語選択に関わる新しい依存追加はありません。
- 比較したもの：変更前の `lectures/01/experiment/run.sh` と、作業ツリー上の `run.sh`、`app/ask.py`、`app/benchmark.py`、ならびに作業計画・要件。
- 調査日：2026-10-26（JST）。
- 外部資料の確認版：Google Shell Style Guide は2026-10-26に確認した現行ページ。Pythonの計時・子プロセス資料はPython 3.12公式ドキュメントを参照。
- 注意：外部スタイルガイドは判断材料であり、この講義の学習目標や利用者の希望に優先する規則ではありません。

## 今回なぜ Python runner に移したのか

### 変更前に確認できたこと

変更前の `run.sh` は `git show HEAD:lectures/01/experiment/run.sh` で確認した当時の版です。

- 233行のBashスクリプトで、モデルを順に回し、各モデル3回 `uv run python -m app.ask` を起動していました。
- `app.ask` の人間向け出力から token 数などを `sed` で抽出し、成功・失敗・回答をBash配列に保存していました。
- 待機、集計、Markdownテンプレート差し込み、回答のコードフェンス化、レポート保存もシェル側で行っていました。
- 既定では1つの質問を2モデルに各3回送り、合計6回のAPI呼び出しでした。API応答時間の統計は記録していませんでした。

### 今回の変更で選んだ構成

- `app/ask.py` の `ask_with_metrics()` が Gemini SDK 呼び出しの直前・直後に `time.perf_counter()` を読み、回答・usage metadata・経過秒数を `AskResult` にまとめて返します。
- `app/benchmark.py` が実験条件の検証、モデル×質問×試行の実行、失敗記録、集計、Markdownレポート生成を行います。
- `run.sh` はリポジトリルートへ移動して `uv run python -m app.benchmark "$@"` を起動する9行の入口になりました。
- 既定の質問は1つから2つになり、モデル2つ・各3回の合計呼び出し数は6回から12回へ倍増しました。複数質問を比較する課題に対応した拡張ですが、実行回数・API利用量・所要時間が変わるため、内部構成の変更とは別に利用者へ明示すべき変更です。

この設計で狙った技術上の利点は、API呼び出し側が token 数と計測値を構造化データとして返し、実験側が人間向けの表示文字列を解析せず扱えることです。`uv run` やプロセス起動、レポート生成に要する時間と API 呼び出し時間も分けられます。既存CLIを1試行ごとに起動する代わりにrunnerを1プロセスにまとめ、実験ループをテストしやすくする効果もあります。

Pythonの `time.perf_counter()` は短い経過時間の計測に使う高分解能カウンターとして公式に説明され、戻り値の差を使う関数です。したがって今回のようにAPI呼び出しの前後で差を取る計測方法には合っています。ただし、**計時関数にPythonを使う必要はあっても、実験全体の制御までPythonへ移す必要があるとは限りません**。シェルからPythonのAPI呼び出しコマンドを繰り返し起動し、そのAPI呼び出し内部で計時する構成も可能です。

### 判断の問題点

作業計画・要件には「Python runnerが実験ループとレポートを担当し、`run.sh` は互換ラッパー」と記載していました。したがって実装は計画と整合しています。一方、「同じコマンドから起動できる」という互換性を強調し、**シェルにあった実験処理を移すこと自体がユーザーにとって大きな方式変更である**点を、選択肢・影響・理由とともに個別に確認しませんでした。また、既定のAPI呼び出し数を6回から12回へ増やすことも、利用条件の変更として目立つ形で確認すべきでした。計画への合意を、実装方式や利用条件の明示的な選択と同じだと扱うべきではありませんでした。

## 判断基準

| 観点 | シェルを主にする | Pythonを主にする |
|---|---|---|
| 主な仕事 | コマンド実行、環境変数やパスの受け渡し、短い順次処理 | API/SDK利用、複雑な条件検証、データ変換、統計、構造化レポート |
| データ | 行単位のテキストやプロセス終了コード中心 | 型のある値、辞書・リスト、JSON/API応答、欠損値や例外 |
| 制御の複雑さ | 単純なループや分岐 | 入れ子の条件、複数条件の組み合わせ、エラーを記録して続行する流れ |
| 外部ツール | 既存コマンドを組み合わせるのが自然 | 使う処理に成熟したSDK・ライブラリがある |
| レポート | 固定形式への短い出力 | 入れ子データ、エスケープ、複数軸の集計、テンプレートへの複雑な差し込み |
| 保守性 | Bashに慣れた受講者が、目的のシェル学習もできる | Pythonの型・テスト・データ構造を使ってロジックを分割できる |
| 注意点 | 複雑なテキスト解析やデータ保持が増えると壊れやすくなる | 実行環境・起動経路を増やし、シェル学習の目的を弱める場合がある |

次の順で判断します。

1. **主目的がプロセス連携か、データ処理か。** コマンドを少数つなぐならシェルを優先し、構造化データの検証・集計・変換が中心ならPythonを候補にします。
2. **処理の複雑さを具体的に見る。** ネストした条件、複数の可変条件、再利用可能な値の受け渡し、例外後の継続、複雑なMarkdown/JSONの生成が増えるほどPythonに傾きます。
3. **実行環境を確認する。** Bash、Python、SDK、必要なバージョンが利用者の環境で確実に使えるか、どの実行方式が講義の目的に合うかを調べます。
4. **利用条件と互換性を比べる。** 既定のモデル・質問・試行回数、API呼び出し数、待ち時間、レポート形式、終了コードを比較します。方式変更を伴わない機能拡張も、API利用量や実行時間を増やすなら事前に知らせます。
5. **既存契約と学習目的を確認する。** 同じコマンドを維持しても、中でどの言語が主役かは利用体験に影響します。学習課題の対象がシェルなら、保守性のためのPython化よりその要件を重く評価します。
6. **大きな方式変更なら先に選択を得る。** 変更行数だけで決めず、方式を保つ案と移す案、影響範囲、利点・不利点を示して確認します。

Google Shell Style Guideは「シェルは小さなユーティリティや単純なラッパーに限る」「100行を超える、または単純でない制御フローのスクリプトは、より構造化された言語への書き換えを検討する」と勧めています。今回の233行のスクリプトは、この勧告に照らすとPython移行を検討する十分な理由があります。ただしこれは**検討を促す基準**であり、100行を超えたら必ず移すという一般法則ではありません。もとのスクリプトが長くなった理由が、学習課題としてシェル処理を扱うためなら、別の結論が妥当です。

## 実現方法の比較とおすすめ順

| 順位 | 方式 | 仕組み | 利点 | 注意点・欠点 |
|---|---|---|---|---|
| 1 | **基礎・発展を別入口にする** | 基礎用 `run.sh` は従来のBash実装として維持し、発展用 `run-advanced.sh` からPython runnerを起動する。基礎・発展でレポートテンプレートも分ける。 | 基礎でシェルの実装を学べる。発展ではSDKの戻り値や複数条件の集計をPythonの構造化データで扱える。従来の基礎操作と発展実験の実装方式が混同されない。 | 入口・テンプレートが2つになるため、READMEで目的とコマンドを明確に分ける必要がある。 |
| 2 | **発展もシェル主導のハイブリッド** | 発展用シェルが条件と反復・待機・進行を担当し、Pythonの `app.ask` がGemini SDK呼び出しとAPI区間の計時を担当する。結果は人間向け表示を再解析せず、明示した機械可読形式で受け渡す。 | 発展課題でもシェルの処理を学べ、API呼び出しは既存Pythonアプリを再利用できる。 | shellとPythonの境界・データ形式を定める必要がある。JSON出力やレポート補助まで作ると部品数が増えるため、必要最小限にする。 |
| 3 | **Python runner主導で既存 `run.sh` を置換** | `run.sh` は入口だけを担い、Pythonが条件解釈・API呼び出し・繰り返し・集計・レポートを担う。以前の変更がこの方式。 | すでにPython SDKを使うアプリと同じ言語で構造化データを扱える。単一プロセス、テスト可能な設定・集計、明確な例外処理に向く。Googleの複雑なシェルを構造化言語へ、という指針にも沿う。 | 基礎用の既存シェル実装がなくなり、シェルを学ぶ意図に合わない。既存の約233行の処理をPythonへ移す変更は大きく、事前の明示的な選択が必要。 |
| 4 | **実験全体をシェルで完結** | API呼び出し、token数、時間、集計、レポート加工までBashのテキスト処理で行う。 | 言語をシェルだけに限定できる。 | Gemini SDK/API応答はすでにPython側にあるため、結局Python CLIの出力解析が必要になりやすい。ネストしたデータ・欠損値・Markdown生成まで文字列で扱うと、引用符や改行、API出力変更に弱くなる。 |

**おすすめは、現在の希望に対して1位の「基礎・発展を別入口にする」方式です。** シェル学習は基礎用 `run.sh` で実現し、発展用ではAPI結果の構造化・複数条件の集計にPythonを使います。もし発展課題でもシェル自体を学びたい場合には、発展用の制御をシェルに残す2位の案を選べます。以前のPython runner主導案は技術的には成立しますが、基礎用のシェル実装を置き換えるため、ユーザーの学習目的を確認せず既定採用すべきではありません。

## 出典と根拠

1. **Google Shell Style Guide — “When to use Shell”**
   https://google.github.io/styleguide/shellguide.html#s1.2-when-to-use-shell

   2026-10-26確認。シェルは小さなユーティリティ／単純なラッパーに使い、データ操作が少ないときに適すること、100行超または複雑な制御フローなら構造化言語へ書き換えることを推奨しています。Googleのスタイル指針であり、全プロジェクトの規範ではありません。

2. **Python 3.12公式ドキュメント — `time.perf_counter()`**
   https://docs.python.org/3.12/library/time.html#time.perf_counter

   高分解能の経過時間カウンターであり、戻り値そのものではなく2回の呼び出しの差を使うものと説明されています。今回のAPI呼び出し直前・直後の計時に対応する根拠です。

3. **Python 3.12公式ドキュメント — `subprocess`**
   https://docs.python.org/3.12/library/subprocess.html

   Pythonから外部コマンドを起動し、入出力・終了コードを扱う標準機能を説明しています。Pythonを選んでもシェル実行や既存コマンドとの連携はでき、言語の選択は二者択一ではありません。

4. **Google Deshell Playbook**
   https://github.com/google/deshell/blob/main/playbook.md

   2026-10-26確認。既存シェルを別言語へ移行する際の段階的な進め方を示す資料です。移行が必要な場合の参考であり、今回その移行を必須とする根拠ではありません。

5. **リポジトリ内の比較証拠**
   - 移行前：`git show HEAD:lectures/01/experiment/run.sh`。233行。モデル反復、CLI出力からの `sed` 抽出、待機、集計、Markdown作成を含みます。
   - 作業ツリー：`lectures/01/experiment/run.sh` は9行の起動ラッパー、`app/benchmark.py` は471行のrunnerです。
   - 移行前の既定は質問1件×モデル2件×各3回で6リクエスト、新版は質問2件×モデル2件×各3回で12リクエストです。
   - `app/ask.py` の `ask_with_metrics()` はGemini SDK呼び出しを `time.perf_counter()` で計時し、`AskResult` を返します。
   - `learning_log/specs/20261026_llm-benchmarking/plan.md` と `requirements.md` にはPython runner方式が記載されています。ただし、記載があったことはユーザーが方式を個別に選択した証拠ではなく、事前確認を省いたことを正当化しません。

## このレポートからの提案

- `run.sh` を本当にPython runnerのラッパーとするか、シェル主導に戻すかを、コード修正前に選択する。
- シェル主導を選ぶ場合、`run.sh` が担当する範囲（モデル・質問・試行・待機）とPythonが担当する範囲（Gemini SDK・計時・構造化結果、必要なら集計）を先に明記する。
- 実装方法を問わず、API応答区間の計時には単調な高分解能時計を使い、質問・条件・結果を人間向け表示のスクレイピングではなく構造化した値として受け渡す。
- READMEには、ファイル名や起動コマンドが同じでも内部の責務・使う言語が変わる場合はそのことを記載する。
- この調査では実API呼び出しを行っていません。応答速度、無料枠、適用レート制限の実測結果を評価するものではありません。
